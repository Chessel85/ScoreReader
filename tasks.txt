HOW TO USE THIS FILE
  - One line per task. Mark progress by changing [ ] to [x], or [~] for
    in progress. Add notes under a task with a "  > " prefix.
  - "Ref N" points at the numbered functional requirements table in the
    Product Definition Document; "NFR-N" at the non-functional table.
    Go and read the acceptance criteria there before starting a task.
  - Near-term phases (A-C) carry detail. Later phases are deliberately one
    line each - their detail depends on decisions not yet made. Expand them
    when we get there.
  - This file is tracked in git (since 2026-08-05) so it is backed up.
    Commit it along with the code changes each task produces.
  - Completed tasks' notes were spring-cleaned 2026-08-07 down to essential
    outcomes and hard-won gotchas (root causes, non-obvious library
    behaviour) - file-by-file mechanism, test names/counts, and anything
    else recoverable via `git show`/`git log` on the task's own commit were
    cut. Unstarted/partial tasks were left untouched.

PHASE ORDER RATIONALE
  Phase A comes first because four defects in the timeline model gate large
  parts of the spec: notes are not attributed to their real part (blocks
  Ref 7), rests are discarded (blocks Refs 14 and 16), and divisions and
  time signature are read once from the first match (breaks Ref 18 on any
  score that changes either mid-piece). Building playback or filtering on
  top of these means reworking that code later.

  A2 lands before A3-A5 on purpose. Those three all rewrite
  _build_timeline_from_xml, and Refs 17 and 18 are correct today. The
  characterisation tests are what prove they are still correct afterwards.

          1. QMenuBar has no focus policy by default - menuBar().setFocus()
             alone does nothing (moot once the pane count below dropped to
             two, but worth remembering for any future menu-bar focus work).
          2. Qt.ShortcutContext.ApplicationShortcut caused ambiguous-shortcut
             failures once more than one MainWindow existed in the same
             QApplication (true across sequential pytest tests, not just a
             hypothetical) - switched to WindowShortcut, which still fires

          landing on the status bar instead of wrapping to Region 1, and
          fixing that broke a different edge (Region 1 -> status bar instead
          of Region 2). ROOT CAUSE, confirmed by direct experiment:
          QWidget.setTabOrder(a, b) splices into ONE shared window-wide
          focus ring; relocating any node resets its own outgoing pointer as

          the dependency between the calls is circular - no call order
          satisfies it. This is a structural limitation of pairwise chain
          splicing applied to a closed ring, not a bug in how this code used
          setTabOrder - not fixable by reordering. Fixed by abandoning
          setTabOrder/focusNextChild/focusPreviousChild for the regions area
          entirely: MainWindow.focus_next_region/focus_previous_region index
          into a fixed 4-widget list and call .setFocus() directly (D-12) -
          same pattern the status bar's own Tab cycling already used.
          GOTCHA WORTH REMEMBERING: don't use setTabOrder to close a
          focus-cycle loop of 3+ widgets in this codebase.

PHASE E - PLAYBACK ENGINE                                 (10 tasks)
###
PLANNED 2026-08-07 (E1-E7 detailed below; E8-E10 deliberately left as
one-liners - metronome is being left for another session). Three scope
decisions made while planning, all confirmed with the user rather than
assumed:
  - F/S/D and the Space/Ctrl+Space/Shift+Space playback keys are GLOBAL
    (WindowShortcut context, like the existing Ctrl+M/F6), not Note-region-
    scoped like arrow-key timeline navigation. Rationale: D-2 scoped timeline
    navigation to the Note region because those keys mean something else in
    other regions (e.g. Up/Down moving table rows); tempo/transport controls
    have no such collision and are playback-wide settings, not per-row
    navigation.
  - Tempo feedback without Phase D: a 4th status bar field ("Playback tempo:
    X bpm"), not a forced announcement. Reachable via F6/Tab like the
    existing three (C6) - something to read on demand, consistent with the
    Phase D skip above.
  - Multi-tempo scope: MusicData.tempo_bpm stays a single score-wide value
    (today's reality - no sample score has more than one tempo mark). The
    30-300 hard bounds (Ref 12 AC2) are enforced by clamping the OFFSET to
    [30 - tempo_bpm, 300 - tempo_bpm] once at load, not by tracking tempo
    per-position through TimelineBuilder the way time signature/key are
    (A6/C6/D-11). Revisit as its own task if/when a real multi-tempo score
    shows up, same pattern A6/C6 themselves followed.
    > REVISITED 2026-08-07: the user generated "Slow then quick" (files/
      Slow then quick/score.xml, 5 measures, tempo 100 -> 80/140 -> 60) and
      reported playback ignored every marking after the first. Per-position
      tempo tracking built after all - see E1's second FIX note below.

BUG FIX 2026-08-12 (reported by the user, live-tested with a real guitar and
independently against Reaper/reaSynth - every note played about a semitone
sharp, e.g. a written E sounded like F): initially suspected the reported
soundfont (FluidR3_GM's nylon guitar patch), MIDI pitch computation, and a
sample-rate mismatch against the user's actual audio device - all three
tested and ruled out directly (offline fluidsynth.Synth.get_samples()
rendering + autocorrelation pitch measurement, no real audio device needed;
music21 cross-check on the MIDI number; user confirmed their device is
already 48kHz). ROOT CAUSE, found by reproducing the app's own
_init_engine() sequence in that same offline harness: SynthEngine._init_engine
built the synth via `fluidsynth.Synth(gain=0.7)` (no samplerate= argument, so
pyfluidsynth's own 44100 Hz default applied) and only set the intended 48000
Hz afterward via `self._fs.setting("synth.sample-rate", 48000.0)`. But
pyfluidsynth.Synth.__init__ calls new_fluid_synth(self.settings) - creating
the actual DSP engine - using whatever synth.sample-rate is in the settings
object AT THAT MOMENT, before returning; a .setting() call afterward only
updates the stored value, it does not reinitialize an already-created
engine. So FluidSynth was silently rendering audio at 44100 Hz the whole
time while WASAPI opened the output stream at 48000 Hz (to match the real
48kHz device) - playing 44100 Hz worth of samples through a 48000 Hz stream
speeds everything up by 48000/44100 (~1.088x), which shifts pitch up ~147
cents, landing closer to a semitone above (F) than a whole tone (F#) -
exactly the reported symptom. GOTCHA WORTH REMEMBERING: pyfluidsynth's
synth.sample-rate (and likely other settings read at engine-creation time)
MUST be passed to the Synth() constructor itself, not set afterward via
.setting() - the constructor's own samplerate=44100 default silently wins
if omitted. Fix: `fluidsynth.Synth(gain=0.7, samplerate=48000.0)`. Verified
by reproducing both the broken and fixed init sequences offline and
measuring the actual rendered frequency each way; user confirmed live on
real playback afterward. Considered - and explicitly declined by the user in
favour of the existing hardcoded 48kHz - having SynthEngine query the host's
actual default output device format and render at that native rate instead
of relying on WASAPI shared-mode's own resampling to adapt a fixed 48kHz
stream to whatever the real device runs at; shared-mode resampling is
standard, expected OS behaviour (not something this bug depended on - the
bug was an internal 44100-vs-48000 inconsistency within our own code, not a
mismatch against the device), so no change was needed for other users on a
44.1kHz device.

D-1  Rests in one voice alongside sounding notes in another
     Decided 2026-08-04: an explicit rest in the score is an event with a
     step of "rest" and shows as "rest" in the Note region.
     RESOLVED 2026-08-06 in B2: no special-casing needed. Rests carry a real
     (part_id, staff, voice) since A4/A5, exactly like sounding notes, so
     MusicData._visible_notes() filters a rest the same way it filters any
     other note - a rest in a soloed/active voice shows as "rest" in Region
     3, a rest in a filtered-out voice does not appear at all.

D-2  Global navigation keystrokes vs per-widget handling
     DECIDED 2026-08-06: per-widget, scoped to the Note region, not global.
     Already flagged in the spec's own Discussion Points; the user reversed
     the original lean toward global handling - too confusing and not
     standard Windows behaviour to have arrow keys act application-wide when
     they mean something else in other regions. Ref 4 updated accordingly.
     TimelineListWidget.keyPressEvent already handles Left/Right this way;
     C1/C2/C3 extend the same widget rather than adding a MainWindow-level
     event filter or WindowShortcut context. Revisit only if Tab-ping-ponging
     back to the Note region proves inefficient in practice.

D-3  Mechanism for forcing screen reader announcements from PySide6
     Needed for Ref 1 AC4, Ref 3 AC3 and Ref 5. Candidates: QAccessible
     alert events, live-region style updates, or driving the screen reader
     API directly. Decide in D1.

D-4  macOS speech recognition API
     Listed as TBC in the spec. Windows path is SAPI 5.4 /
     Windows.Media.SpeechRecognition. Decide in L3.

D-5  Multi-part GM programs and MIDI channel allocation
     DECIDED 2026-08-06 in A8: one MIDI channel per part (not per staff -
     staves within a part share an instrument in every sample score, and
     per-staff allocation would burn through the 16-channel ceiling faster
     for no observed benefit), assigned in part-list order, skipping
     channel 10 (index 9, percussion), wrapping past 16 parts.
     MusicData.get_channel_for_part() / get_gmidi_program_for_part().

D-6  UK vs US music vocabulary
     RESOLVED 2026-08-10 in F4. Default: UK, unless QLocale.system() resolves
     confidently to a US territory - any other/indeterminate locale stays
     UK. Screen reader announcements: no separate channel needed (Phase D
     was already skipped) - NVDA reads whatever on-screen text the toggle
     produces, so on-screen and spoken wording are automatically the same
     thing. Region 4 attribute names: the internal "measure" key is NEVER
     renamed (storage/menu wiring depend on it staying stable) - only the
     rendered display LABEL changes, via models/vocabulary.attribute_label().
     Surfaces via Options > Terminology Language (a UK/US submenu, not a
     single toggle - see F4's live-tested FIX notes). Scope: bar/measure and
     the duration-name family (crotchet/quaver/etc) only - stave/staff was
     tried and then deliberately excluded, see D-15.

D-7  How tests avoid opening audio hardware
     DECIDED 2026-08-05: constructor injection. MainWindow(synth=None)
     defaults to a real SynthEngine but accepts a stand-in, so tests can
     assert which notes, channel and program would have played - needed by
     Refs 8, 9, 13 and 14. Also makes the engine swappable for the macOS
     driver work in NFR-01.

D-8  Where test sample scores live
     DECIDED 2026-08-05: both. files/ is now tracked in git (66 KB) so the
     real MuseScore exports are backed up and usable as integration
     fixtures, plus hand-written minimal MusicXML under tests/fixtures/ for
     unit tests that need to isolate one behaviour.

D-9  Source of the boundary ("doh") sound - Ref 2 AC4, Ref 3 AC4, see C5
     DECIDED 2026-08-06 in C5: synthesize through the existing SynthEngine -
     a short (quaver-length, ~200ms), quiet, low double-bass note (E2, GM 44
     Contrabass), not tied to the score's own tempo, on a dedicated channel
     (15) reserved from D-5's per-part allocation. No new asset, no
     licensing question (never was going for a literal Homer Simpson
     sample - just a low, unobtrusive indicator that a boundary was hit).
     Making it configurable on/off, and choosing a different instrument/
     pitch, is explicitly deferred until it's actually asked for.

D-10 F6 pane-cycling mechanism and scope - Functional Spec, see C7
     DECIDED 2026-08-06, REVISED 2026-08-06 after live testing: originally
     three panes (menu bar, regions, status bar) - the user's own initial
     spec - but after trying it, the user reversed that: F6/Shift+F6 now
     toggle between just TWO panes, the regions area and the status bar.
     Menu bar access is left to the OS's native Alt mechanism, not F6,
     matching ordinary Windows application behaviour instead of adding a
     bespoke path to something already reachable natively. Mechanism: a
     WindowShortcut-context QShortcut on MainWindow (not
     ApplicationShortcut - see C7's DONE note for why that caused ambiguous-
     shortcut failures) so it fires no matter which child widget holds
     focus. Tab/Shift+Tab keep their existing job of cycling the four
     regions (and, new in C6, cycling a pane's own internal fields for the
     status bar) and stay out of pane-switching entirely. The "regions" stop
     restores whichever region was last focused (tracked via
     QApplication.focusChanged), defaulting to Region 1 before anything has
     been focused - this is a partial answer to the "Focus memory in
     regions" Discussion Point: it remembers the region, not the row within
     it. Since a two-pane toggle has no distinct "reverse", both F6 and
     Shift+F6 call the same _toggle_pane().

D-11 Status bar field tracking and FIFTHS_MAP relocation - Functional Spec,
     see C6
     DECIDED 2026-08-06: key signature (fifths) becomes per-EventSlice state,
     tracked through the score exactly the way A6 already tracks time
     signature (both can change mid-piece, see score_way_to_go) - not a
     separate lookup, not read once at file-open like Region 1's summary
     values. FIFTHS_MAP moves from parsers/musicXML_reader.py to new
     models/key_signatures.py so models/music_data.py can read the current
     position's key without a parsers->models reverse import; Region 1's
     display and the status bar's live display now share one mapping. Status
     bar key wording keeps the existing "/" format ("G major / E minor"),
     not the alternate "or" wording floated during planning - no wording
     change, everywhere stays consistent.

D-12 Region cycle (Tab/Shift+Tab within the MAA) mechanism - Functional
     Spec, see C1/C7
     DECIDED 2026-08-06, after a second live-tested Tab bug (see C7's second
     FIX note): QWidget.setTabOrder cannot reliably close a 4-widget loop at
     all here - not a matter of getting the call order right, a structural
     limitation (relocating any one of the four widgets to fix one edge
     necessarily breaks another, and the four required relocations form a
     genuine cycle of dependencies). Region cycling now bypasses Qt's global
     focus chain entirely: MainWindow.focus_next_region/focus_previous_region
     index into a fixed 4-widget list and call .setFocus() directly, and
     RegionTableWidget/Region2ListWidget/TimelineListWidget's Tab/Backtab
     handlers call those instead of window().focusNextChild()/
     focusPreviousChild(). This is the same pattern C6's status bar fields
     already used for their own internal Tab cycling (StatusBarWidget.
     focus_field(), never routed through the global chain) - now applied
     consistently to the regions area too. No more QWidget.setTabOrder calls
     anywhere in the app.

D-13 Version numbering - Functional Spec, see C8 (About dialog)
     DECIDED 2026-08-06: semantic-ish X.Y.Z in version.py, starting at

D-14 Metronome click sound synthesis - Ref 14, see E8/E11
     OPEN 2026-08-07: not decided, deliberately parked as functional debt.

D-16 setCurrentRow(row)'s one-arg form does NOT default to NoUpdate
     FIXED 2026-08-10, live-tested regression, found right after F2. F3's
     fix for "a single-note slice has nothing for NVDA to announce after
     selectAll()" (see Selection-driven regions in CLAUDE.md) was written on
     the assumption that QListWidget.setCurrentRow(row) - the plain one-arg
     overload - uses QItemSelectionModel::NoUpdate internally, so it could
     set the current item after selectAll() without touching the selection.
     Confirmed by direct test against this PySide6 build that it does not:
     it collapses the selection down to just `row`. That silently broke
     "moving onto a chord selects and sounds every note in it" - only the
     first note in a multi-note slice stayed selected and sounded. Fixed by
     passing the flag explicitly: setCurrentRow(0,
     QItemSelectionModel.SelectionFlag.NoUpdate) in
     MainWindow._update_timeline_views. Regression test:
     test_navigating_onto_a_chord_selects_and_sounds_every_note in
     tests/test_main_window.py. Lesson for future Qt selection-model code in
     this app: don't trust an overload's assumed default command without
     checking it against the actual PySide6 build in use.

D-17 Up arrow did nothing at the top of a chord's selection
     FIXED 2026-08-11, live-tested regression, found during Phase G testing
     (unrelated to G itself). Landing on a chord selects every note in it,
     current row 0. Down correctly narrowed the selection to row 1 - Qt's
     native ExtendedSelection arrow handling collapses a multi-row selection
     to the new current row, but only as a SIDE EFFECT of the current row
     actually changing. Up at row 0 has nowhere to move, so it silently
     no-op'd and left the whole chord selected instead of narrowing to the
     top note. Fixed in TimelineListWidget.keyPressEvent by explicitly
     clearing selection and reselecting currentItem() after every Up/Down,
     not just relying on the native move to do it - a no-op when the native
     handling already collapsed correctly, and the actual fix at a boundary.
     Regression test:
     test_up_arrow_at_the_top_of_a_chord_collapses_selection_to_the_first_note
     in tests/test_main_window.py.

D-18 Region 2 rebuild clobbered a restored Ref 27 voice filter on reload
     FIXED 2026-08-11, live-tested regression, found testing Phase G (G1).
     MainWindow._on_score_loaded applied a saved ScoreConfig
     (MusicData.apply_config, correctly setting active_voice_filter) BEFORE
     calling _update_ui_regions, which rebuilds Region 2 from scratch via
     load_score_structure - that resets every node back to enabled=True and,
     through the very same filter_changed signal a live Region 2 toggle
     uses, silently overwrote the just-restored filter back to "everything
     on". Net effect: a saved "voice off" toggle (e.g. the user's own repro -
     switching off Viola in Way To Go.mxl) came back on after every reload,
     even though attribute order (which doesn't route through Region 2)
     persisted correctly. Fixed by snapshotting the restored filter before
     _update_ui_regions runs, then handing it to a new
     Region2ListWidget.apply_active_voice_tuples() afterward - restores
     Region 2's own per-node on/off state (inferring a whole part/staff was
     toggled off whenever every voice under it ends up inactive, so the UI
     collapses the same way the original toggle would have) and re-emits
     filter_changed through the normal signal path, the same one a live
     toggle already uses. Regression test:
     test_voice_filter_persists_across_reload_of_same_file in
     tests/test_main_window.py.
     > FOLLOW-UP 2026-08-11 (live-tested, found right after D-18 above): the
       filter itself was restored correctly (Region 2 showed the toggled
       voice off, subsequent navigation excluded it) - but
       _update_ui_regions's own initial audition (play_all=True) fired
       BEFORE apply_active_voice_tuples ran, so the very first sound heard
       on load still included the voice that was supposed to be off (user's
       own repro: hearing both flute and viola on load despite viola being
       correctly shown/enacted as off from that point on). _update_ui_regions
       now takes a play_all param; _on_score_loaded passes play_all=False
       when there's a filter to restore and fires the audition itself
       (_play_selected_region_3_notes) only after
       region_2.apply_active_voice_tuples has run - one correct audition,
       not one wrong one followed by a silent correction. Regression test:
       test_initial_audition_on_reload_respects_the_restored_voice_filter.
