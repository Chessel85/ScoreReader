This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Notifications

Handled automatically by Stop/Notification hooks in `~/.claude/settings.json` (SAPI text-to-speech) — fires on every session end/permission prompt/question without needing this instruction followed manually. No action needed here.

## Project

"Recall Score" (local folder `SReader`, GitHub repo `RecallScore`) — a screen-reader-first music score and guitar-tab viewer/editor for visually impaired musicians. `Product Definition Document.md` is the authoritative spec: roles, numbered functional requirements with acceptance criteria, the 2x2 region layout, and the intended keystroke map. Read the relevant requirement rows before implementing a feature; most current code maps directly onto them (e.g. pickup-bar measure numbering is Ref 17, TS-relative beat/duration units is Ref 18, part/staff/voice filtering is Ref 7).

Accessibility is the product, not a polish item: notes are rendered as spoken-friendly text ("F sharp", "B double flat", octave omitted in the note list), navigation is keyboard-driven with a cyclic region focus loop, and every timeline move triggers MIDI audition. Ref 9 sets a 25 ms audition latency budget — that constraint is why the audio path is in-process FluidSynth rather than an external MIDI port. Preserve these properties when changing UI or data formatting.

## Commands

Windows, Python 3.13, dependencies in the checked-out `.venv` (not tracked):

```powershell
.venv\Scripts\python.exe main.py          # run the app
.venv\Scripts\Activate.ps1                # then plain `python main.py`
```

Dependencies are split: `requirements.txt` (runtime — PySide6 6.11, music21 10.5, pyfluidsynth 1.4, python-rtmidi 1.5), `requirements-dev.txt` (pytest, pytest-qt, pytest-cov), and `requirements-build.txt` (pyinstaller — only needed to build the Windows installer, see Packaging below). `mido` is no longer used or installed (python-rtmidi, added for live MIDI input below, is unrelated — a direct RtMidi binding, not mido). No linter is configured.

```powershell
.venv\Scripts\python.exe -m pytest                    # whole suite (~0.6s)
.venv\Scripts\python.exe -m pytest -m "not slow"      # skip music21 tests
.venv\Scripts\python.exe -m pytest tests/models/test_music_data.py::test_name
.venv\Scripts\python.exe -m pytest --cov=models --cov=parsers --cov=widgets
```

**`tests/manual/`** holds two refactor-verification harnesses (`parser_fingerprint.py`, `model_fingerprint.py`) — **not** pytest tests (pytest only collects `test_*.py`, so they are never picked up). They fingerprint every timeline-builder output, and everything `MusicData` answers, across every score file in `files/`/`examples/`/`tests/fixtures/`, and `--check` a fresh run against a baseline captured from an earlier revision. Use them as the acceptance gate for any change to `parsers/` or `models/` that is meant to be behaviour-preserving — "the tests pass" is not evidence for that kind of change. See `tests/manual/README.md` for the git-worktree baseline workflow.

Two invariants the harness enforces, both guarded by tests in `tests/test_harness.py`:

- **No window opens.** `tests/conftest.py` sets `QT_QPA_PLATFORM=offscreen` before PySide6 is imported.
- **No audio device opens.** An autouse fixture blocks `SynthEngine._init_engine`, so constructing a real engine in a test fails with a pointer to the fix. `MainWindow(synth=...)` accepts any object with the `SynthEngine` interface; `tests/support/null_synth.py` records calls so tests can assert what *would* have sounded.

Timeline tests must build `MusicData(file_path=...)` directly — that walks the XML with ElementTree in ~1 ms. Going through `MusicXMLReader.load()` also runs music21 at ~460 ms; those tests carry the `slow` marker.

VS Code launch config is "Python: Current File" (debugpy) — debug by opening `main.py` and pressing F5.

## Local binaries (never commit these)

`audio/synth_engine.py` needs native FluidSynth DLLs in `bin/` and a SoundFont at `soundfonts/Airfont_380_final.sf2` (~263 MB). Both directories are gitignored and exist only in the working tree. (Switched from the earlier `FluidR3_GM.sf2` because its piano/viola patches bake a dual hard-left/hard-right zone layer into every note — a common GM soundfont "stereo width" trick that a channel's MIDI pan CC can only partially offset — which defeated the Mixer dialog's pan feature (wishlist #4). Airfont_380's patches pan correctly.)

**This is load-bearing.** The 148 MB soundfont exceeds GitHub's 100 MB file limit; committing it in August blocked all pushes and cost two days to recover. Never `git add` these paths, never remove those `.gitignore` entries, and if you need to restore them use `git cat-file blob <sha> > <path>` — `git checkout <commit> -- bin/` stages the files and reintroduces the problem.

If the binaries are missing the app still runs: `SynthEngine` sets `FLUIDSYNTH_AVAILABLE = False`, prints a warning, and every playback call becomes a no-op.

## Packaging (Windows installer)

Three independently runnable steps produce `dist_installer/RecallScore-Setup-<version>.exe` — a standard NSIS wizard (Welcome/Components/Directory/Start Menu/Install/Finish) that installs to Program Files (per-machine, requires admin — a deliberate choice, confirmed with the user) and registers a real uninstaller under Add/Remove Programs. All are plain command-line tools the user runs directly (the user wanted to be able to run these themselves without going through Claude), **in this order**:

```powershell
.venv\Scripts\python.exe -m PyInstaller packaging\VoiceWorker.spec --noconfirm   # from repo root - MUST run first, RecallScore.spec bundles its output
.venv\Scripts\python.exe -m PyInstaller packaging\RecallScore.spec --noconfirm
cd packaging; makensis installer.nsi   # NSIS 3.11's ${__FILEDIR__} resolves wrong given a relative path with a directory component (e.g. `makensis packaging\installer.nsi` from the repo root) - run it from inside packaging\, see installer.nsi's header comment
```

`packaging/build_installer.ps1` still exists as an **optional** one-command wrapper (`powershell -File packaging\build_installer.ps1`) that chains the three steps with a couple of sanity checks (venv present, `bin`/`soundfonts` present, finds `makensis.exe` on PATH or in one of the two standard `Program Files` locations) — none of the steps depend on it.

- **`packaging/VoiceWorker.spec`** — PyInstaller onedir build of the hands-free voice-control worker (Ref 19, `audio/voice_recognition_worker.py`) as its **own separate executable**, `console=True`. **Reported bug (2026-08-26)**: the installed `.exe` logged `"vosk/sounddevice not available; voice control disabled"` on every attempt to enable it, even on a machine with the feature working fine in dev. Root cause was three compounding packaging gaps, not a runtime bug: (1) `audio/voice_recognition.py` never imports `vosk`/`sounddevice` itself — only the worker script does, in a separate child process, specifically to dodge a DLL-name collision with FluidSynth's bundled MinGW runtime DLLs (see that module's own docstring) — so nothing in `main.py`'s import graph ever reached them, and a single combined PyInstaller build never discovered or bundled either package; (2) even installed, the old launch command (`sys.executable <path to voice_recognition_worker.py>`) can't work once frozen — `sys.executable` **is** `RecallScore.exe` (no separate `python.exe` ships), and the `.py` source isn't shipped as a loose file (it's compiled into the app's own PYZ archive); (3) a `console=False` build nulls `sys.stdout`/`stdin`/`stderr` at bootstrap regardless of whether the process is given piped handles (the same quirk `main.py`'s `_redirect_stdio_if_headless` works around for `print()`), which would break the worker's newline-delimited-JSON stdio protocol even if 1 and 2 were fixed. Fixed by building the worker as its own `console=True` executable (real stdio pipes) via this spec, launched by `audio/voice_recognition.py`'s `_worker_command()` with the Windows `CREATE_NO_WINDOW` `subprocess.Popen` flag so the console window is never actually shown. Explicitly collects `libvosk.dll` (+ its own bundled MinGW runtime copies) via `collect_dynamic_libs("vosk")`, since `vosk/__init__.py`'s `open_dll()` `dlopen`s it relative to `dirname(vosk.__file__)` — not discoverable via PyInstaller's normal import-graph binary scan; `sounddevice`'s own PortAudio DLL needs no equivalent handling, `pyinstaller-hooks-contrib`'s bundled `hook-sounddevice.py` covers it automatically. `audio/voice_recognition.py`'s `VOSK_AVAILABLE`/`MODEL_DIR`/`WORKER_EXE` are frozen-aware: `find_spec("vosk")` would always report unavailable in the frozen **main** app process by design (vosk is only ever bundled into this separate worker exe), so frozen availability checks `WORKER_EXE`'s existence instead; `MODEL_DIR` needed no change at all, since it already resolves via the same `sys._MEIPASS`-relative `__file__`-faking trick documented below for `PROJECT_ROOT`/`BIN_DIR`.
- **`packaging/RecallScore.spec`**'s own **`vosk_model_large/`** and **`voice_worker/`** bundling — the ~205MB Vosk speech model (gitignored, not pip-installable — see `.gitignore`'s own note on where to get one) and `VoiceWorker.spec`'s already-built `dist\RecallScoreVoiceWorker\` output, added via `Tree(...)` (post-`Analysis`, since `Tree()` needs the already-built TOC to extend) rather than the plain `datas` list the rest of this spec uses. Both are guarded exactly like `icon_path`/`has_icon` below — missing either prints a `[WARN]` and degrades this build to "no voice control" rather than failing it, since voice control is a supplementary feature and the app is fully usable without it. `voice_worker/` is bundled as a **subfolder of `RecallScore`'s own dist output**, specifically so `packaging/installer.nsi`'s plain recursive `File /r "${DIST_DIR}\*.*"` copy needs no changes at all to pick it up.

- **`version.txt`** (repo root) — the single, manually-maintained source of truth for the app version, read by `version.py` (the About dialog, `widgets/about_dialog.py`), `packaging/RecallScore.spec` (Windows exe version resource), and `packaging/installer.nsi` (installer filename/registry `DisplayVersion`). Edit it by hand to bump the version; nothing derives or auto-increments it. `version.py` resolves it via the same `sys._MEIPASS`-aware idiom as `main.py`'s `_app_icon_path()`, so it works both in dev and once `RecallScore.spec` bundles it into the frozen app.
- **`packaging/RecallScore.spec`** — PyInstaller onedir build of `main.py`, runnable standalone. Bundles `bin/*.dll` and `soundfonts/Airfont_380_final.sf2` (the gitignored local binaries above) into the frozen app so the installed app needs no separate download — this works with zero changes to `audio/synth_engine.py`'s `PROJECT_ROOT`/`BIN_DIR` resolution, because PyInstaller fakes frozen modules' `__file__` to a path under `sys._MEIPASS` matching the source tree, so `dirname(dirname(audio/synth_engine.py))` still lands on the bundle root. Excludes music21's bundled example-score corpus (`collect_data_files(..., excludes=["corpus/**", ...])`, ~58 MB) since the app only ever calls `converter.parse()` on the user's own file, never `music21.corpus` — and excludes `matplotlib`/`PIL` entirely, which music21 declares as hard dependencies purely for its unused `graph`/`audioSearch` plotting modules (only those two subpackages import matplotlib anywhere in music21). Also bundles `docs/user_guide.html` (opened from Help > User Guide, same `sys._MEIPASS`-aware resolution), `version.txt`, and, if any exist, `examples/*.xml`/`*.musicxml`/`*.mxl` (opened via File > Open Example Score...) — the last two resolved by the same `_app_base_dir()` idiom as `_app_icon_path()` below. Also regenerates `packaging/version_info.txt` from `version.txt` on every run (see below) — moved into the spec itself so it runs standalone with no wrapper script required.
- **`docs/user_guide.md`** / **`docs/user_guide.html`** — the end-user guide, reachable in-app via Help > User Guide. The `.md` is the maintained source; the `.html` is a **checked-in, manually regenerated** artifact (deliberately not a build step, to avoid making `pandoc` a build dependency) — after editing the `.md`, regenerate with `pandoc docs/user_guide.md -s --toc --metadata title="Recall Score User Guide" -o docs/user_guide.html` and commit both together.

- **GOTCHA (Windows, `console=False` build)**: a `console=False` build (required — a GUI app shouldn't flash a console window) runs with `sys.stdout`/`sys.stderr` set to `None`, not just closed. This app's error handling is `print("[ERROR] ...")`-based throughout (see "Known gaps" below), so the moment anything on that path prints — e.g. `SynthEngine._init_engine` catching a WASAPI open failure on a machine with no sound device — `print()` itself throws `AttributeError: 'NoneType' object has no attribute 'write'`, which PyInstaller's bootloader surfaces as "Failed to execute script 'main'" (this was the user's first launch, on a Windows 10 VM with no audio hardware). ## Architecture

Package-per-domain layout; each module holds one class. Data flows one way:

`main.py` → `MainWindow` → `MusicXMLReader.load()` → `MusicData` → four region views + `SynthEngine`

- **`models/`** — `note_data.py` (`NoteData`), `event_slice.py` (`EventSlice`), `parts_structure.py` (`PartStructureInfo`), and `music_data.py` (`MusicData`, the aggregate + timeline builder).

  **`MusicData`'s five collaborators (S1, 2026-08-27)** — `MusicData` had grown to 2,481 lines and ~110 methods spanning seven unrelated jobs. The logic now lives in five classes, each built once in `__post_init__`, each holding a back-reference to the `MusicData` it serves and **owning no score state of its own** (so none of them can go stale against the score, and none needs rebuilding when a field changes):
  - **`timeline_navigator.py`** (`TimelineNavigator`) — cursor movement (Refs 2/3/5/6): Left/Right, Ctrl+Left/Right, Home/End, typed-measure jump, and the per-measure first/last-visible-index lookups Region 5's span jumps and Find share. **Also owns the filter-dependent visibility caches** — `MusicData._invalidate_visibility_cache` is now a delegator to `TimelineNavigator.invalidate_cache`.
  - **`note_renderer.py`** (`NoteRenderer`) — Ref 15 AC4's attribute display system: Region 3's row text, Region 4's rows, and the per-voice which/order state. The state itself (`voice_display_attributes`, `attribute_order`) stays on `MusicData` because `export_config`/`apply_config` persist it; only the reading and mutating moved.
  - **`playback_event_builder.py`** (`PlaybackEventBuilder`) — note grouping into `(channel, program, pitches, duration_ms[, bank])` events plus the grace-note side channel, quarters-to-ms conversion, and both stepping functions (`next_visible_event_index` and the repeat/ending/Segno/Coda/D.C./D.S./Fine-aware `next_playback_index`).
  - **`override_manager.py`** (`OverrideManager`) — every override that mutates already-parsed notes in place: part name/instrument (S5), percussion item name/sound (wishlist #8), whole-piece key signature (S6). Grouped because each is applied from both a dialog's OK and `apply_config`, and each is losslessly re-derivable from an immutable original the parser recorded (`percussion_source_key`, `file_key_fifths`).
  - **`find_index.py`** (`FindIndex`) — the Find dialog's target catalog and occurrence scanner. See the **Comprehensive Find** note below.

  **`MusicData` keeps a one-line delegator for every method these took over**, including the private ones tests drive directly (`_note_attribute_pairs`, `_format_note_for_region_3`, `_sounding_bounds`, `_slice_is_navigable`, `_quarters_to_ms`). That is deliberate and load-bearing: `MusicData` is replaced wholesale on every load, so no caller may hold its own collaborator — everything must keep asking `MusicData`. Put new behaviour in the collaborator that owns it, not in `MusicData`; adding a method there is only right if it is a delegator or genuinely cross-cutting.

  Verified behaviour-preserving with `tests/manual/model_fingerprint.py` across all 56 score files in `files/`, `examples/` and `tests/fixtures/`, before and after — navigation walks, Region 3/4 text, playback/grace events, durations, ring-out, bar bounds, jump-aware playback walks, every Find target's full occurrence list, percussion items, the performance report, and key-override round trips: 86,496 lines, zero differences (the same R4-style harness approach used for `TimelineBuilder._scan_first_part`).

  **`models/` no longer imports from `parsers/` (S2, 2026-08-27).** It previously did so five times, including a *private* name (`parsers.midi_timeline_builder._spell_pitch`), and `MusicData.__post_init__` imported all four timeline builders at module scope. Because `TimelineBuilder`/`UgTimelineBuilder` import music21, that made merely importing the data model cost **461 ms and 706 modules**; it is now **45 ms and 111 modules**, with music21 not loaded at all. Four changes did it:
  - **`models/synthetic_parts.py`** — the identifiers for parts/voices this app FABRICATES: `CHORDS_PART_ID`/`CHORDS_PART_NAME`/`LYRICS_PART_ID`/`LYRICS_PART_NAME`, `GP_CHORD_VOICE_ID`/`GP_CHORD_VOICE_NAME`, `STAVE_TEXT_VOICE_ID`/`STAVE_TEXT_VOICE_NAME`. These had been **defined independently in three parser modules** (`"chords"`/`"lyrics"` in both `timeline_builder.py` and `ug_timeline_builder.py`; the display names a third time in `ug_reader.py`, plus GP's own `CHORD_VOICE_NAME` in `gp_reader.py`) — every pair having to agree verbatim, since `collapsed_part_ids` matches part_ids by string and `get_performance_report_lines` joins names by exact text. That is the R5 bug class, latent. One definition now; the parser modules re-export what they already published.
  - **`models/pitch_spelling.py`** — `spell_pitch` (was `parsers.midi_timeline_builder._spell_pitch`), plus the two pitch-class tables. Both `MidiTimelineBuilder` (parse time) and `OverrideManager` (S6 key-override re-spelling) need it, and it is pitch arithmetic over a fixed table, not parsing.
  - **`models/strum_codes.py`** — UG's undocumented strum-code vocabulary. The **full 9-code table** (`STRUM_CODES: Dict[int, StrumSlot]`, `StrumSlot(stroke, effect)`) taken verbatim from UG's own front-end bundle (webpack module `78736`): `1/101` down/up, `2/102` down/up muted, `3/103` down/up accented, `201` palm mute, `202` pause, `203` real pause. The app previously knew only 3 and **mislabelled `202` (a pause — the commonest code in every real pattern) as "muted strum"**. `slot_words(code)` is the spoken form ("down", "down muted", "palm mute", "pause", …; unknown → `"code N"`); `strumming_pattern_text(codes)` the Region 1 credit. A pure lookup table, same category as `models/gm_instruments.py`. **`models/strum_pattern.py`** (`StrumPattern(name, bpm, denominator, is_triplet, codes)`) is one parsed pattern plus `slots_per_bar()`/`bar_count()`/`slot_ms()`/`slot_labels()`/`slot_rows()` — the beat-position label vocabulary shared with the talking metronome is **`models/beat_position_words.py`** (`spoken_word_for_beat_position` + its tables, extracted from `audio/position_announcer.py`, which re-exports them). **`models/section_span.py`** (`SectionSpan(label, start_measure, end_measure)`) is a named song section, populated by `UgTimelineBuilder` today and published through `models/timeline_build.py` like every other side-channel list.
  - **`parsers/timeline_builder_factory.py`** (`builder_for`/`build_timeline`) + **`models/timeline_build.py`** (`TimelineBuild`) — the format dispatch moved to `parsers/` where it belongs, while `models/` keeps the contract. `TimelineBuild.apply_to(music_data)` is one assignment site for all twelve builder outputs, so a field added to a builder but forgotten here can't silently read as a default. **`MusicData.__post_init__` imports the factory function-locally, deliberately** — that is what keeps the documented `MusicData(file_path=...)` shortcut (the ~1 ms ElementTree path timeline tests rely on) working while deferring the parser/music21 cost to the moment a file is actually parsed. Don't "tidy" that import up to module scope; it would reinstate both the layering inversion and the import cost.

  Verified by the same 56-file fingerprint as S1 (zero differences against the pre-S1 baseline) plus an end-to-end load through all four readers.
- **`parsers/musicXML_reader.py`** — `MusicXMLReader` builds header/metadata: credits, key, time signature, tempo, per-part structure (staff→clef, staff→voices, GM program). It parses the file **twice**: raw `ElementTree` for credits/part-list/clefs, and `music21.converter.parse` for tempo/key/time, with the ElementTree values as fallback when music21 returns nothing. `_extract_part_structure_etree`'s `<part-name>` read populates `PartStructureInfo.name`, and **`TimelineBuilder` derives `NoteData.part_name` from that same `parts_info`** rather than re-reading the XML itself (R5, `TimelineBuilder._part_names`) — anything keying off both (e.g. the Performance Report's per-instrument note tally) is therefore consistent by construction. Previously these were two independent reads that had to agree verbatim, and they diverged: a non-ASCII `<part-name>` (a MuseScore export with a Korean instrument name) got replaced by `_extract_part_structure_etree` with a hardcoded `"Classical Guitar"` fallback while `TimelineBuilder` kept the real text, so the report showed "0 notes" for a fully-noted part. The ASCII-only filter was removed (nothing else in the app filtered non-ASCII names) and R5 made both readers share one source so they can't drift again. `TimelineBuilder` keeps an ElementTree fallback only for the no-reader path (`MusicData(file_path=...)` built directly, used by timeline tests, which has no `parts_info` at all).

  **Synthetic Chords/Lyrics parts from `<harmony>`/`<lyric>` markup** — a real notated MusicXML score with chord symbols and lyrics (e.g. a MuseScore lead-sheet export) gets the same "an instrument called Chords" / "lyrics are also an instrument/part" UX established for Ultimate Guitar import, but bucketed into the SAME slices as the real notated part (real measure/beat positions already exist here, unlike UG's fabricated positions). `CHORDS_PART_ID`/`CHORDS_PART_NAME`/`LYRICS_PART_ID`/`LYRICS_PART_NAME` and `has_harmony_elements(root)`/`has_lyric_elements(root)` live in `timeline_builder.py` and are imported into `parsers/musicXML_reader.py`'s `_extract_part_structure_etree` — one shared source rather than two independent reads that could drift (the R5 bug class). `MusicXMLReader` adds the two `PartStructureInfo` entries (one staff, one voice each — not zero; a part with no staff/voice nodes is invisible to `Region2HierarchyModel.get_active_voice_tuples()`, the same gotcha documented for MIDI/UG below) only when the file actually has the markup, and `TimelineBuilder` independently detects the same markup while walking notes.

  A `<harmony>`'s root/kind/bass resolves to MIDI pitches and a display label ("G7", "F/C") via `music21.harmony.ChordSymbol(root=..., kind=..., bass=...)`, accepting MusicXML's own `kind` vocabulary directly (first established by `ug_timeline_builder.py`'s chord-symbol parsing, reused here), with a bare-root-triad fallback and finally the label alone with no `chord_pitches` if even that fails — a malformed `<kind>` shouldn't make the whole bar's chord entry vanish.

  **`models/vocabulary.spell_out_minor_chord`**: a chord label's minor abbreviation is usually a bare trailing "m" ("Am", "Am7") — NVDA reads that as the letter "m", not the word "minor", while every other abbreviation seen in practice (`Cmaj7`, `Dsus4`, `C7`, bare `G`) already reads correctly. A regex (root + accidental, "m" not followed by "aj" so `Amaj7` is untouched, optional extension digits, optional `/bass`) rewrites just that case to "A minor"/"A minor 7"/etc; `AmM7` (minor-major-seventh) is deliberately left unhandled. Lives in `models/vocabulary.py` rather than `timeline_builder.py` because three independent chord-symbol sources all need it and share no other code: MusicXML `<harmony>` here, Ultimate Guitar's raw `[ch]` markup (`parsers/ug_timeline_builder.py`), and Guitar Pro's chord diagram name (`parsers/gp_timeline_builder.py`, applied once where the sticky `current_chord_name` is set). One shared function applied at each format's own "raw chord text becomes a display label" point, rather than three copies of the same regex.

  A `<lyric>`'s `<text>` becomes a Lyrics-part `NoteData` in the same `(measure, offset)` bucket as the melody note it came from — silent by design (`midi_pitch=None`, like UG's Lyrics part), and simply absent (not a `"No lyrics"` placeholder) wherever a note has no `<lyric>` child, since real per-note timing already exists here, unlike UG's need to mark an explicit "nothing to say" bar.

  A `<notations/arpeggiate direction="up"/"down">` on a single (non-chord) note has no real notation meaning — arpeggios apply to chords — so it's read as a per-note pick/strum-direction indicator instead, reusing `NoteData.strum`'s existing "down stroke"/"up stroke" vocabulary. **Reported, redesigned**: this was first attached directly to the melody note carrying the mark, which meant the data was invisible in normal use (Region 3 showed the plain step name unless the user opened the attribute menu) and conceptually wrong besides — "strumming does not take place on a piano... strumming is for guitars and would be associated with the chord instrument" (the user's framing). Fixed by moving it off the melody note entirely: `TimelineBuilder.build()` tracks a per-part sticky "current chord" (pitches + label, the same "last named chord carries forward" convention GP/UG use for their own Chords voice/part, updated whenever a `<harmony>` is seen), and an arpeggiate mark now produces an extra Chords-part **stroke** `NoteData` at that beat — sticky chord's pitches/label plus the stroke's own `strum` — instead of touching the melody note. A bar can therefore carry several Chords entries; a stroke with no chord known yet (arpeggiate before the piece's first `<harmony>`) is skipped rather than fabricating one. Sticky-chord state is scoped per part, not per document — every real file seen carries `<harmony>`/`<notations/arpeggiate>` on a single part, and interleaving correctly across multiple parts would need cross-part time-ordered measure walking that `TimelineBuilder` doesn't do. **Reported again, second pass**: a bar whose own `<harmony>` lands at the same beat as its one stroke-marked note produced two near-identical Chords rows at that slice, read as noise rather than information. `TimelineBuilder.build()` now tracks `harmony_notes_by_key` (a `(measure, offset) -> NoteData` map, scoped per part like the sticky-chord state); a stroke landing on a key already in that map sets `.strum` on the SAME `NoteData` instead of appending a second one. `MusicXMLReader.load()` then defaults the Chords part's `voice_display_attributes` to `{"step", "beat position", "strum"}` (same "audible immediately" default `GpReader` established for GP's synthetic Chords voice), while the real Piano voice stays at `{"step"}`. Both synthetic parts sort after every real part in a slice's pitch order.

- **`audio/synth_engine.py`** — in-process FluidSynth. At import it prepends `<root>/bin` via `os.add_dll_directory` + `PATH` and pre-loads the glib/gobject/gthread/fluidsynth DLLs with `ctypes.CDLL` before `import fluidsynth`; that ordering is required on Windows and is why the module has side effects at import time. The synth runs on the WASAPI driver at 48 kHz with a 128-frame period and 2 periods — low-latency settings chosen for Ref 9; don't raise them without cause. `fluidsynth.Synth(gain=0.7, samplerate=48000.0)` — **GOTCHA**: `samplerate` **must** be passed to the `Synth()` constructor itself. `pyfluidsynth.Synth.__init__` calls `new_fluid_synth(self.settings)` (the actual DSP engine creation) using whatever `synth.sample-rate` is in the settings object at that exact moment, before returning; a `self._fs.setting("synth.sample-rate", ...)` call made *after* construction only updates the stored value and has no effect on the already-created engine — it silently keeps rendering at pyfluidsynth's own 44100 Hz constructor default. That mismatch (audio actually generated at 44100 Hz, WASAPI stream opened at 48000 Hz to match the real device) speeds everything up by 48000/44100, audible as ~147 cents sharp — closer to a semitone above than a whole tone, which is exactly how it was first reported (every note played a semitone sharp). WASAPI shared mode (no exclusive-mode setting anywhere in this code) is relied on to resample this fixed 48 kHz stream to whatever a given user's device actually runs at — standard OS behavior, deliberately not second-guessed with device-format detection (see tasks.txt's E10-adjacent BUG FIX entry for the user's explicit call on this). Note-off is scheduled by one single-shot `QTimer` **per sounding group**, not one shared timer — each part rings for its own `duration_ms` independent of the others (see the GM programs paragraph below). `play_chord(events, retrigger=True)`: the default silences everything currently sounding first (`stop_all_notes()`), correct for discrete audition (Ref 8 AC2 — Region 3 navigation, chord audition) where each move/press should present a clean slate. `Sequencer` passes `retrigger=False` for its natural step-to-step advance during real playback (Ref 10) — reported bug: with the default, a new part's attack (e.g. Violin I entering mid-phrase) was silencing *other*, unrelated parts' still-ringing notes, since the old unconditional `stop_all_notes()` had no way to know the new group had nothing to do with them. `Sequencer.play_from()`/an explicit reposition still calls `stop_all_notes()` itself first, so restarting playback elsewhere does clear the deck — only the in-run advance is non-destructive.
- **`audio/metronome.py`** / **`soundfonts/recall_score_sounds.sf2`** (Ref 14, tasks.txt E11/D-14) — the click metronome's sound is a second, small, project-authored soundfont loaded by `SynthEngine._load_click_soundfont` alongside the main GM soundfont (its own `sfid`, `self._click_sfid`), not a synthesized tone or GM percussion — both were tried and rejected as unsatisfying.   **GOTCHA, resolved 2026-08-12 (user question, tasks.txt E12's own follow-up)**: `SynthEngine.play_click`/`play_word` used to also take no `duration_ms` param but internally schedule an explicit note-off via a `QTimer`, timed from each sample's own natural length — read from a sidecar `soundfonts/recall_score_sounds.sf2.json` (`tools/wav_to_sf2.py` wrote it alongside the `.sf2`, keyed by `(bank, program, pitch)`, since different presets can validly reuse the same note numbers for unrelated sounds). That sidecar/scheduling turned out to be unnecessary and was removed: each click/word zone is a one-shot, non-looping sample (`SampleModes=0`), and FluidSynth deactivates such a voice on its own once the sample's data is exhausted, *regardless of whether a note-off was ever sent* — holding the note "on" and simply never releasing it early is sufficient to let it play to its natural end. `_stop_click()`/`_stop_announcement()` (still called from `stop_all_notes()`, and from `play_click`/`play_word` themselves before a new one starts) remain the deliberate-*interrupt* path — only the "wait exactly N ms then auto-release" scheduling was removed, not the ability to cut a still-ringing one-shot short on purpose. `tools/wav_to_sf2.py` no longer writes the `.sf2.json` sidecar at all (see its own module docstring) — nothing in the app reads one anymore.

- **`audio/position_announcer.py`** (Ref 28, tasks.txt E12) — the position announcer ("talking metronome"), built on the same custom soundfont as the click (`soundfonts/recall_score_sounds.sf2`'s `talking_metronome_default` preset, bank 0/program 0, notes 60-69 = one..seven/e/and/a per `tools/config.ini`). `spoken_word_for_beat_position(beat_position)` splits the ts-relative beat position into a whole part (1-7 → number word, Ref 28 AC3) and a fractional remainder (25/33/50/66/75% → e/and/and/a/a, AC4); `announcement_event_for_beat()` wraps that into a `(channel, bank, program, pitch, velocity)` tuple, same shape as `metronome.py`'s `click_event_for_beat()`, and both `Sequencer._sound_current_step` and `MainWindow._play_selected_region_3_notes` call it right alongside (not instead of) the existing click call, gated by its own independent `MusicData.position_announcer_enabled` (AC1/AC2) rather than the metronome's. **Testing note that follows from this**: assert the cycle *method runs*, not just where focus lands — `test_every_region_routes_tab_through_the_region_cycle_not_qts_focus_chain` in `tests/test_main_window.py`. GM programs are **1-indexed in the model** (25 = nylon guitar, from MusicXML `<midi-program>`) and **0-indexed on the wire** — `MusicData.get_playback_events_for_indices` does the `-1` conversion per part, so don't convert twice. Each part gets its own MIDI channel (`MusicData.get_channel_for_part`, skipping all three reserved channels in `MusicData.RESERVED_CHANNELS` — percussion channel 10/index 9, the position announcer's channel 9/index 8 (Ref 28), and the Performance region's change-cue channel 8/index 7 (Ref 29)) so a chord spanning two parts plays both instruments instead of collapsing onto `parts_info[0]`'s program (A8, Ref 8, D-5) — `SynthEngine.play_chord` / `NullSynth.play_chord` take the resulting `(channel, program, midi_notes, duration_ms)` groups and sound them together. The usable-channel list is computed fresh inside `get_channel_for_part` on each call, not cached as a class attribute — a class-body list comprehension can only see its own outermost iterable, not other class attributes referenced inside its condition.

`duration_ms` is per-group, not per-slice: `get_playback_events_for_indices` derives each part's own duration from the `max` `quarter_length` of *that part's* notes at this slice, not from `EventSlice.quarter_length` (which is `min()` across every note bucketed into the slice, from **every** part — see `TimelineBuilder.build`). **Reported bug**: a slice-wide duration meant one part's short note clamped every other part sounding at the same instant — one voice's fast notes were cutting a slower voice's sustained notes short. `SynthEngine.play_chord` schedules note-off with one independent `QTimer` per group (not a single shared one) so this holds even across a single `play_chord` call with mixed-length groups.

### Timeline model

The timeline is a flat, sorted list of `EventSlice` — one entry per distinct `(measure, offset_in_quarters)` with at least one sounding note. Rests are skipped, so navigation lands only on attacks. `active_event_index` is the cursor; `move_timeline_left/right` return `bool` (False at the boundaries, where the spec wants an audible boundary cue that isn't implemented yet).

**`TimelineBuilder.build()`'s structure (S3, 2026-08-27)** — `build()` was a single ~560-line method nesting five loop levels, with `pending_grace`/`pending_dynamics`/harmony/stave-text/percussion state all interleaved in one scope. It is now 84 lines showing only the shape of the walk (part → measure → element), dispatching each measure child to the handler that owns it, in the same style `_scan_first_part`/`_step_barline`/`_step_wedge` already used for the structural scan:

- **`_handle_direction`** (dynamics, deferred to a note at the same offset; stave text, bucketed immediately), **`_handle_harmony`** (the Chords entry + the sticky chord), **`_handle_note`** (the note itself plus what rides along with it — a lyric, a Chords-part stroke), which calls **`_read_pitch`** (`<pitch>`/`<unpitched>` → name/octave/sounding key/percussion voice override) and **`_read_notations`** (technical/articulations/dynamic/arpeggiate/lyric). **`_flush_pending_grace`** and **`_assemble_slices`** close out the measure and the build.
- **Three small state objects** carry exactly what has to survive between elements, which is what the old single scope made impossible to see: **`_PartState`** (what persists across a part's measures — divisions/time signature/key carried forward, the sticky current chord, `harmony_notes_by_key`), **`_MeasureState`** (reset per measure — the offset walker, `pending_dynamics`, `pending_grace`), and **`_NoteSink`** (the `(measure, offset)` buckets plus each slice's time signature and key).
- **`_NoteSink` is the one place that writes both `buckets` and `slice_state`**, which the old code repeated at five separate call sites. Its `overwrite_state` flag preserves the two distinct conventions exactly: a real note stamps its slice's state unconditionally, while stave text and harmony entries only `setdefault` (they are `<measure>` children that can precede the notes they sit with). `append_only` is for a note riding along with one already bucketed there, which never sets the state itself.
- **`_PartState.beat_position`** replaces three separate copies of the "pickup bars start at the end of a notional bar" calculation (notes, stave text, harmony), and **`_displaced_offset_divs`**/**`_staff_number`** replace the duplicated `<offset>`/`<staff>` reads. **`refresh_bar_shape` deliberately does not write back to `time_sig_num`/`time_sig_den`** — those exist only to seed the next measure's walker, and `carry_forward` is the single place that sets them; keeping the two roles apart is what preserves R17's "mid-measure `<attributes>` affects offsets after it, but measure *length* comes from the barline" split.

Verified with the R4-style parser diff harness — now permanent as `tests/manual/parser_fingerprint.py` — across all score files in `files/`, `examples/` and `tests/fixtures/` (56 files, 9,354 slices, 27,946 notes), dumping every field of every `EventSlice` and `NoteData` plus `beat_markers` (450), `tempo_changes` (22), `repeat_spans` (7), `ending_spans` (12), `hairpin_spans` (18), the Segno/Coda/To Coda/Fine/navigation marks (33) and `total_measures`: **zero differences**. Nesting went from 8 levels to 5 by the same measure.

`TimelineBuilder.build()` (`parsers/timeline_builder.py`) is a third hand-rolled `ElementTree` pass, separate from `MusicXMLReader`. music21's stream is stored on `MusicData.score` but is **not** the source of truth for notes — the DOM walk is, because it handles `<backup>`/`<forward>` offsets, `<chord>` grouping, and `notations/technical` string/fret data explicitly.

Two conventions the parser enforces, both spec requirements:

- **Pickup bars** are detected by `implicit="yes"` or by measure 1's staff-1 content summing to less than a full bar. When present every measure number shifts down by one, so the pickup is measure **0** and the first full bar is **1**. Pickup notes get beat positions placing them at the *end* of the notional bar.
- **Beat positions and durations are relative to the time-signature denominator**, not to quarter notes. `beat_unit_quarter_len = 4.0 / denominator`; a quarter note is `ts_duration` 1.0 in 4/4 but 2.0 in 7/8. `NoteData.quarter_length` is kept separately for playback timing.
- **`notations/technical` and `notations/articulations`/`ornaments` children can repeat on one note** — e.g. a rasgueado marks one note with three `<pluck>` children (p/i/m/a) together. Always read them with `.findall()`, never `.find()` — `.find()` silently returns only the first match and drops the rest (F3's real-world bug, caught against a live MuseScore export; see `tasks.txt` F3 and the `multi_value_technical.musicxml` fixture).
- **`<grace>` notes** carry no `<duration>` at all, so `_MeasureOffsetWalker.step()` never advances `offset_divs` past one — reported bug: a grace note landed at the exact same `(measure, offset)` as the note it decorates and rendered as a phantom extra chord tone (a real acciaccatura, `allegro-first-movement-from-sonatina-no-1-in-g-trinity-grade-2-piano.mxl` bar 5, showing "A, B" instead of "A grace B"). `TimelineBuilder.build()` buffers one or more consecutive grace notes per `(staff, voice)` in `pending_grace` (reset per measure, same convention as `pending_dynamics`) and attaches them to the next non-grace note's `NoteData.grace_notes` (a `List[GraceNote]`, `models/note_data.py`) instead of bucketing them as their own slice — a grace note never gets an `EventSlice`/row of its own. `slash="yes"` (acciaccatura, a "crushed" grace note) vs. absent/`"no"` (appoggiatura, traditionally a longer grace note that steals time from the main note) is captured on `GraceNote.slash` but **realized identically for now** — both just ring briefly before the main note; true appoggiatura time-stealing is unmodelled. A trailing, unresolved grace note (last note of a voice/measure being itself a grace note - untested by any real file) is flushed as an ordinary standalone note at measure end rather than dropped. `MusicData._note_attribute_pairs`'s `"step"` value becomes `"A grace B"` (the main note's own step name, then the literal word "grace", then the grace step names, comma-joined for a multi-note grace group) whenever `grace_notes` is set — shared by Region 3 and Region 4 since both read that same pair. Playback: `MusicData.get_grace_note_events_for_indices`/`get_grace_note_events_at_index` mirror `get_playback_events_for_indices` (grouped by part, `(channel, program, pitches)`, no `duration_ms` — a grace note has none) but are a **separate** side channel, not merged into the main pitch list, which is what stacking used to do. `audio/strum_schedule.py`'s `sound_events` dispatcher routes to the new `SynthEngine.play_chord_with_grace` whenever `grace_events` is non-empty (a UG score never has any — MusicXML-only, see the two independent `elif`/`else` branches); that method sounds the grace note(s) immediately for `audio/grace_note_schedule.effective_grace_duration_ms`'s clamped duration (default 60 ms, capped to half the shortest main note's own `duration_ms` so a fast tempo/short note value can't have the pre-note outlast what it decorates) via the same one-QTimer-per-pending-attack shape `play_strum_pattern` already established (`SynthEngine._pending_grace_timers`, cancelled by `stop_all_notes()` alongside `_pending_strum_timers`), then fires the main chord on a delay via the ordinary `play_chord(..., retrigger=False)`. Guitar Pro has its own native grace-note concept in the `.gp` format and MIDI has none at all (a grace note is indistinguishable from an ordinary very short note there) — both out of scope for this pass, MusicXML only.

**Performance markings (Ref 29)** — repeat/ending spans (and barline-style points) come out of **`TimelineBuilder._scan_first_part`**, one walk of `root.find("part")` that also produces `measure_start_quarters`, each measure's `(ts_num, ts_den, fifths)`, and `tempo_changes`, returned together as a `_FirstPartScan`. R4 consolidated this from four separate methods that each re-walked the same measures independently, each with its own copy of the measure-number parse and, for three of them, its own offset walker — four chances for the pickup/offset handling to drift apart. Reading from the first part only is the deliberate "structural, not per-voice" convention (`_detect_pickup` does the same): time signatures, tempo markings and barlines are score-wide properties.

**Hairpins are per-part, not first-part-only** (2026-08-29). `<direction-type>/<wedge>` is collected in the per-part walk (`TimelineBuilder._step_wedge`, called from `_handle_direction`), because a wedge on any staff of any part must be reported — `examples/pachelbels-canon-in-d-string-quartet.mxl` has 154 wedges across all 6 parts, of which the old first-part-only scan saw 18. `_PartState.open_wedges` is keyed `(staff, number)` and each value is a **stack** (not the single most-recent-wins slot `open_direction_spans` uses): a long hairpin with shorter ones nested inside it is a real notation concept (`files/etude 2.mxl`), so a `<wedge type="stop">` closes the innermost (most recently opened) wedge first — nested pedals/dashes are not a thing, so those stay single-slot. A `stop` with an empty stack emits `HairpinSpan(kind="", start_known=False)` (the kind of a bare stop is unknowable); a wedge still open when its part ends is flushed by `_flush_open_wedges` with `end_known=False`. Both synthetic positions exist only so containment / Ctrl+End resolve — the `*_known` flags are what the Region 5 / report wording keys off ("no start marked in the file" / "no end marked in the file"). `self.hairpin_spans` is sorted by `start_quarters_from_start` at the end of `build()` so the multi-part collection is chronological. `HairpinSpan` gained `part_id`/`staff`/`number`/`start_known`/`end_known` (all defaulted). Plain-text `<words>` dynamics/tempo instructions ("cresc.", "rall.") are also classified in `_handle_direction` via `models/vocabulary.py`'s `dynamics_instruction_kind`/`tempo_instruction_label` (narrow whole-text allow-lists, never a substring sweep) and emitted as point `DirectionMark`s (`kind="dynamics_word"`/`"tempo_word"`) — the same word still stays a Stave Text event too (per-note reading vs. score overview). Find gains `dynamics_instruction`/`tempo_instruction` marking kinds for them. **R17**: measure *length* is computed from the time signature snapshotted at the measure's first `<attributes>` (a time signature change takes effect at a barline), while every other consumer reads the walker's live value, so a mid-measure `<attributes>` still affects offsets after it — those two readings previously differed by accident and are now explicit. Verified behaviour-preserving by diffing slices/tempo changes/spans/beat markers/`total_measures` from the pre- and post-refactor parsers across every score file in `files/`, `examples/` and `tests/fixtures/`: zero differences. That harness is now permanent — `tests/manual/parser_fingerprint.py`. The spans populate `MusicData.repeat_spans`/`ending_spans`/`hairpin_spans` (`List[RepeatSpan]`/`List[EndingSpan]`/`List[HairpinSpan]`, `models/repeat_span.py`/`ending_span.py`/`hairpin_span.py`) as side-channel outputs, the same `tempo_changes` pattern (sparse markers scanned against the current position) — **not** a per-`EventSlice` field like `time_sig`/`key_fifths`, since spans are rare, not "in effect at literally every slice". Repeat/ending containment is a plain measure-number range check (barlines only occur at measure boundaries); hairpin containment compares `EventSlice.quarters_from_start` against `HairpinSpan.start_quarters_from_start`/`end_quarters_from_start`, since a `<wedge>` can start/stop mid-measure. `<barline>/<repeat direction="forward"|"backward">` pairs are tracked with a single "currently open forward repeat" slot (most-recent-wins on an unclosed second forward — nested repeat barlines aren't a real notation concept) and a `<barline>/<ending number type="start"|"stop"|"discontinue">` is tracked per open number, closed by the next `stop`/`discontinue` for that same number — validated against `files/bach-bourree-tab/score.xml`'s two real repeat+1st/2nd-ending passages. A backward repeat with no preceding forward defaults its start to measure 1 (the standard notation reading of an unmarked opening repeat; untested by any real file this app has seen, only by the hand-authored `tests/fixtures/unmatched_backward_repeat.musicxml`). `MusicData.total_measures` (also populated in `build()`, from `max(measure_start_quarters.keys())`) is the whole-score bar count for the Performance Report below — deliberately **not** derived from `timeline_slices`, which would undercount a trailing all-rest measure (rests are skipped from `timeline_slices` entirely).

`MusicData.get_performance_region_rows(index=None)` resolves the target slice (default the cursor) and returns two `PerformanceRegionRow`s (`models/performance_region_row.py`) per active span — a start line and an end line, repeats first then endings then hairpins, each in span-list order (a stable, deterministic order the label-diff in `MainWindow._refresh_region_5` depends on). Row wording follows one generic `"<thing> start"`/`"<thing> end"` pattern throughout (user-requested, not `"Start <thing>"`/`"End <thing>"`) — `"Repeat start: bar 2"`/`"Repeat end: bar 3"`, `"Ending 1 start"`/`"Ending 1 end"`, `"Crescendo start"`/`"Crescendo end"`. Row wording goes through `vocabulary.bar_word(uk_terms)` like the status bar, never a hardcoded "bar"/"measure" literal — "bar" vs "measure" is a dialect choice, not a fixed pick (confirmed with the user). Hairpin rows **state the full range** so one row read alone conveys it — `"Crescendo start: bar 1 beat 3, to bar 2 beat 2"` / `"Crescendo end: bar 2 beat 2, from bar 1 beat 3"` — with each endpoint via `_bar_beat_label(bar_word, measure, beat_position)` (beat suffix only when not on the downbeat). An unmatched wedge gets a single row: `"Diminuendo start: bar 23, no end marked in the file"` (or the `"Hairpin end: bar 25, no start marked in the file"` mirror; `kind==""` reads as "Hairpin"). D5: hairpin rows are part-name-prefixed only when more than one part has a hairpin, via `MusicData._marking_part_prefix` (the generalised former `_dir_prefix`). Repeat/ending rows never name a beat, since barlines only occur at measure boundaries (beat 1) by construction. Plain-text `dynamics_word`/`tempo_word` marks get a one-shot row (`'Crescendo (marked "cresc.")'` / `"Tempo instruction: rall."`), after the direction-line rows and before the P4 barline/clef rows. `slice_index_at_or_after_quarters(quarters)` and `last_visible_event_index_of_measure(measure)` (the latter mirroring the existing `first_visible_event_index_of_measure`, but scanning for the LAST match instead of the first — nothing else in the app needed a "last event in a measure" concept before) are the two lookups Region 5's Ctrl+Home/Ctrl+End use to resolve a row's jump target: a hairpin row's `jump_target_quarters` is set (a wedge can start/stop mid-measure) so it always uses the quarters-based lookup; a repeat/ending row's is `None`, resolved via the plain measure lookup instead — Ctrl+Home uses `first_visible_event_index_of_measure`, Ctrl+End uses `last_visible_event_index_of_measure` (the user's own decision: "the end of it" means the *last* sounding note of the end bar, not the first). `MusicData.get_performance_report_lines()` (Edit > Performance Report..., `widgets/performance_report_dialog.py`) is a separate, read-only, whole-score summary — reuses `get_region_1_data()` wholesale (not cherry-picked keys, since `credits_dict`'s keys come from each file's own `<credit-type>` text and aren't guaranteed to match a fixed name like "Title"), counts notes per instrument from `_real_timeline_slices` (the whole score, ignoring the current Region 2 filter — the report describes the piece, not the current filtered view), and lists `repeat_spans`/`ending_spans` by bar range. Its **Dynamics** section is one chronological list merging hairpins (part-prefixed like everything else now), plain-text `dynamics_word` point marks (`'Crescendo (marked "cresc."): Measure 10'`), and point `<dynamics>` marks; an unmatched hairpin carries the same "no start/end marked in the file" wording. A dashed/bracket line drawn under a "cresc." is reported **separately** under `Dashed lines:` / `Bracket lines:` as written — two things in the file, two lines. `Tempo instructions:` (omitted when zero, like `Rehearsal marks:`) and `To coda marks:` sections were added. No jump-to-location navigation from the report — an explicit scope cut from the user for this iteration, unlike Region 5's own Ctrl+Home/Ctrl+End.

`get_performance_region_rows` also emits a **one-shot** row — no start/end pair, unlike the three span kinds above — for a time-signature or immediate/point tempo change landing exactly on the resolved slice: it compares `EventSlice.time_sig` (already tracked per-slice by both `TimelineBuilder` and `MidiTimelineBuilder`, so no new data model was needed) and the raw `_tempo_change_at(index)` tuple — not the divided display float, to avoid a float-precision false positive, and deliberately not `effective_tempo_bpm`/`playback_tempo_display_bpm`, which reflect the user's absolute playback-tempo setting (Ref 12) and would make changing it look like a score change — against the immediately preceding slice in whichever list the resolved slice came from. Never fires at index 0 — the opening signature/tempo is already shown in Region 1 and the status bar every load, so alerting on it in Region 5 too would just be noise. Reuses hairpins' `jump_target_quarters` jump mechanism as-is: both Ctrl+Home/Ctrl+End resolve to the row's own position (a harmless no-op, since the alert only ever shows where the cursor already is), so no new navigation code was needed. Accelerando/ritardando (a span, like a hairpin) is explicitly out of scope — nothing parses it yet, and it needs its own investigation into how the user's scores actually encode it before it can be designed.

`MainWindow._refresh_region_5` is hooked into the single choke point `_update_timeline_views` (unconditional of `play_all`) rather than scattered across every navigation method — confirmed exhaustive by reading `main_window.py`/`audio/sequencer.py` in full: every path that moves `active_event_index` (arrow/measure/typed-measure navigation, Home/End, Region 2 filter changes, Sequencer/Ref-10 playback stepping, initial load) already funnels through there. It diffs the new row-label list against `self._last_performance_row_labels` and skips the rebuild (not just the audio cue) when unchanged, so Region 5's own focus/selection isn't reset on every navigation step while the cursor stays inside the same span(s). **GOTCHA**: that sentinel must start as `None`, not `[]` — starting it at `[]` made the very first render (an empty opening position, whose own rows are also `[]`) compare equal and get silently skipped, leaving Region 5 with no items at all rather than its documented "None" placeholder row.

**Reported bug**: `_update_timeline_views` calls `_play_selected_region_3_notes()` (when `play_all`) **before** `_refresh_region_5()`, not after — the cue was audible during Space-driven playback but silent on every manual navigation step (arrow keys, Ctrl+arrow, Home/End, typed-measure jump) until this was fixed. `_play_selected_region_3_notes` calls `synth.play_chord(events)` with its default `retrigger=True`, which calls `stop_all_notes()` first thing (A8) — with the cue fired first, that `stop_all_notes()` landed a fraction of a second later and cut the just-started cue off almost immediately. Playback never hit this because `_on_sequencer_step` calls `_update_timeline_views(play_all=False)`, so `_play_selected_region_3_notes()` never runs there at all — the Sequencer already sounded its own chord via `_sound_current_step`'s `retrigger=False`, which never calls `stop_all_notes()` (see the GM programs paragraph above). Fixed by reordering: sound the notes (and their retrigger-driven silence-everything) first, then fire the cue on its own untouched reserved channel afterward.

### Selection-driven regions

Region 3 is `ExtendedSelection` and defaults to selecting every note in the current slice (`Ctrl+A` reselects all). Regions 4 and audio follow the **selection**, not the slice: `get_region_4_data_for_indices(indices)` and `get_midi_notes_for_indices(indices)` take Region 3's selected rows. `_update_timeline_views(play_all=...)` blocks Region 3's signals during a rebuild to avoid audition storms, then fires playback once. `get_region_3_data()` and all three indices-taking accessors read through `MusicData._visible_notes()` first, which filters the current slice's notes by `active_voice_filter` — the `(part_id, staff, voice)` set Region 2 maintains (Ref 7) — so a selected row index always means the same note in Region 3, Region 4 and playback even when some notes are hidden. Keep view code reading through these accessors rather than reaching into `timeline_slices`.

After any Region 3 rebuild that calls `selectAll()`, also call `region_3.setCurrentRow(0, QItemSelectionModel.SelectionFlag.NoUpdate)` **outside** the `blockSignals` window (`_update_timeline_views` does this). `selectAll()` marks rows selected but deliberately leaves the view's own "current" item untouched, and Qt's accessibility bridge needs a definite current item to tell NVDA which note to announce — with several notes selected NVDA still gets a selection-changed announcement, but with exactly one note there was nothing pointing at it (live-tested bug, F3). The explicit `NoUpdate` flag is required — the plain one-arg `setCurrentRow(0)` was believed to default to `NoUpdate` and leave `selectAll()`'s selection alone, but in this PySide6 version it doesn't: it collapses the selection down to just row 0, silently turning "moving onto a chord sounds every note in it" into "only the first note sounds" (live-tested regression, caught after F2). Always pass the flag explicitly; don't rely on the one-arg overload's default here.

Region 3's row text and Region 4's rows both go through an attribute system beyond the bare note name (Ref 15 AC4), split into a WHICH half (F1) and an ORDER half (F2). WHICH: `voice_display_attributes` (keyed by `(part_id, staff, voice)`) is which optional keys (`string`, `fret`, `dynamic`, `articulation`, `fingering`, `pluck`, ...) are switched on per voice — defaulting to just `{"step"}`. `_note_attribute_pairs(note)` returns only the keys that note actually has a value for, so a key renders in Region 3/4 only when it's **both** toggled on for that voice **and** present on the note; absence isn't a bug; it's the mechanism. `set_display_attribute(key, scope, notes, add)` fans a toggle out across `"voice"/"stave"/"part"/"score"` scope, driven by Region 4's context menu (`Region4TableWidget`). ORDER: `MusicData.attribute_order` is the live, mutable, per-instance rendering order both `_format_note_for_region_3` and `_region_4_rows` iterate — `DISPLAY_ATTRIBUTE_ORDER` is only the fixed *default* every fresh `MusicData` starts from (`__post_init__`), not what actually renders. `move_attribute_order(key, up, within=...)` reorders it; `attribute_keys_for_voices(voice_tuples)` scans the whole score (not just the current slice) for which keys are relevant to a scope. `attribute_order`, unlike `uk_terms`, is **per-score** (Phase G, Ref 27) — persisted via `persistence/score_config.py` and restored in `_on_score_loaded` through `MusicData.apply_config`; a fresh `MusicData` with no saved config falls back to `DISPLAY_ATTRIBUTE_ORDER`. Options > Reorder Attributes... (`widgets/attribute_order_dialog.py`, `AttributeOrderDialog`) is the F2 UI: scoped to whichever part/staff/voice is selected in Region 2 (`Region2ListWidget.current_node()`, `region2_manager.voice_tuples_for_node()`), Move Up/Move Down buttons (Alt+U/Alt+D mnemonics) move the selected attribute live. It deliberately doesn't duplicate F1's add/remove menu. Adding a new optional per-note attribute (as F3 did for dynamic/articulation/fingering/pluck) needs no UI work at all — append it to `DISPLAY_ATTRIBUTE_ORDER` and `_note_attribute_pairs`, and the toggle menu, scope fan-out, ordering, and omit-if-absent rendering all pick it up automatically.

### Comprehensive Find (P0–P6, 2026-08-28)

Navigation > Find... (`Ctrl+F`, `widgets/find_dialog.py`; Alt+Right/Alt+Left step next/previous from anywhere in the window via `NavigationController`). Governing principle: **anything in the score that is not a plain note, a rest or a lyric is findable**, and that is structural, not a list we keep extending. Full design + phase-by-phase edit log in `find_feature_plan.md`. Two mechanisms:

- **Attribute target** — a per-note fact. A new `Optional[str]` field on `NoteData`, populated in the parser, emitted from `NoteRenderer.note_attribute_pairs`, appended to `MusicData.DISPLAY_ATTRIBUTE_ORDER`. Find, Region 3/4 rendering, the toggle menu, Reorder Attributes and `.rsc` persistence pick it up for free. Keys added by this work: `tie`, `slur`, `tuplet`, `fermata`, `arpeggio` (chord notes only — D7), `accidental` (cautionary/editorial only — D14), `technique` (technical marks beyond fret/string/fingering/pluck), `glissando`, `grace` (a spoken summary of `grace_notes`), `other_notation` (D6 catch-all), `chord_symbol`, `chord_diagram`. New fields default `None`, so the MIDI/GP/UG builders are unaffected except where they opt in (P5: GP's `tied`/`slide` now fill `tie`/`glissando` so Find is cross-format).
- **Marking target** — a structural fact not attached to a timeline note. A model in `models/`, populated in `TimelineBuilder`, published through `models/timeline_build.py` (`from_builder` + `apply_to` — every field lands in one place), a `MARKING_KINDS` entry + a branch in `FindIndex.candidate_indices_for_target`, and (per D15) a Region 5 row + Performance Report line. Kinds added: `DirectionSpan`/`DirectionMark` for pedal, octave-shift, rehearsal, dashed/bracket lines and a `other_direction` catch-all (D6); `BarlineMark` (double/other, never the final `light-heavy` — D16), `ClefChangeMark`, `MeasureStyleMark`. These lists default empty in `TimelineBuild`, so non-MusicXML formats show none of them.

**Value-level Find (D1/D2).** `FindTarget` carries an optional `value`. For the keys in `find_target.VALUE_EXPANDED_KEYS` (an explicit allow-list — `articulation`, `technique`, `dynamic`, `accidental`, `tie`, `slur`, `glissando`, `tuplet`, `chord symbol`, `other notation`) the dialog offers an "any" row plus one row per distinct value found; every other key stays a single "any" row however many values it holds. Comma-joined multi-value keys are matched by membership over the split list, never `==`. The occurrence cache in `FindIndex` is keyed `(key, value)` and dropped by `invalidate_cache()` from `MusicData._invalidate_visibility_cache`.

**Occurrence counts (D13).** Every dialog row ends with `"N occurrences"` / `"1 occurrence"` (`find_target.occurrence_label`). A count is `len(sorted_candidate_indices(target))` — timeline *positions*, so a chord of three staccato notes counts once — computed via the cached path in `available_targets_with_counts()`, not a second scan. Attribute counts respect the Region 2 voice filter; marking counts don't (markings are structural, like Region 5) — documented in the user guide §5.7.

**Two catch-alls (D6) are the completeness guarantee.** `_read_notations` keeps a `_RECOGNISED_NOTATION_TAGS` frozenset; any other `<notations>` child becomes `other_notation` = `tag.replace("-", " ")`. `_handle_direction` does the same via `_RECOGNISED_DIRECTION_TYPE_TAGS` → an `other_direction` `DirectionMark`. Both are presence-filtered, so a score with none shows nothing extra; both are covered by tests feeding an invented element name.

**Not made audible (out of scope, unchanged standing decision).** Ties, arpeggios, ornaments, pedal, octave shift stay label-only; `<octave-shift>` does not transpose playback. See the Known gaps ornaments entry.

## Known gaps

- Parsing errors are swallowed with `print("[ERROR] ...")` and partial state. Ref 25 / NFR-06 call for an accessible error dialog; prefer moving that way over adding more silent prints.
- Not yet built despite being specified: voice control, edit mode, MIDI export (import is done, Ref 25), Guitar Pro/BME I/O, capo handling, chord naming.
- Metronome click sound (Ref 14) is functional but not satisfying - two synthesis attempts (a sawtooth lead, then GM percussion Claves) were both live-tested and found lacking. Tracked as functional debt, not a missing feature; see tasks.txt E11 / D-14.
- **Voice control (Ref 19), SAPI 5.4 spike abandoned 2026-08-24** - a full hands-free implementation against Windows SAPI 5.4's classic in-process recognizer (`SAPI.SpInprocRecognizer`, driven via `pywin32`'s `win32com.client` automation bindings) was built and live-tested on the user's real machine (Windows 11, build 26200), then abandoned in favour of a Vosk-based rewrite (see tasks.txt L1) - not for lack of effort, but because the underlying engine's own accuracy proved inconsistent even for this app's small, closed command vocabulary once every plumbing bug below was fixed: "stop"/"pause"/"back" recognized reliably (~90%+ confidence), "play"/"preview"/others frequently not recognized at all. The code itself is preserved, uncommitted-to-`main`, on branch `feature/voice-control` (see that branch's own preservation commit) purely for reference - none of it should be revived as-is, but the findings below are real and would resurface for anyone trying classic SAPI again:
  - SAPI's own `AudioInput` device-token registry category (`HKLM\SOFTWARE\Microsoft\Speech\AudioInput\Tokens`, the MSDN-documented way to enumerate/select microphones for automation) does not exist on this Windows build at all (`SpObjectTokenCategory.SetId` fails with `SPERR_NOT_FOUND`, 0x8004503A) - the legacy "Windows Speech Recognition" microphone-setup wizard that used to populate it has been removed, replaced by the architecturally separate "Voice Access" feature, and running that replacement doesn't repopulate the old hive. Real per-device names ARE obtainable regardless, via the classic `winmm` `waveInGetNumDevs`/`waveInGetDevCapsW` API (`ctypes`, stdlib only) - confirmed working, surfaced the real hardware (a Realtek onboard mic, a Behringer USB interface) SAPI's own token category couldn't see.
  - `ISpeechRecoGrammar.CmdLoadFromMemory(GrammarData, LoadOption)` - MSDN documents `GrammarData` as accepting the grammar XML directly as a string - reliably fails with `E_INVALIDARG` (0x80070057) through `win32com`'s dynamic dispatch, regardless of grammar content, `LANGID`, engine token, or whether the XML is passed as `str` or `bytes`. `CmdLoadFromFile` against the identical XML written to a real temp file succeeds immediately. Looks like a `win32com` VARIANT-marshaling quirk specific to that one method's dynamically-generated wrapper, not a problem with SAPI or the grammar itself.
  - `SpInprocRecognizer` has NO audio input wired by default - unlike what most SAPI automation examples (which target `SpSharedRecognizer`, tied into the OS's own shared recognition service) imply. It constructs fine, loads a grammar fine, and reports its own `.State` as Active, but delivers zero `OnSoundStart`/`OnHypothesis`/`OnRecognition`/`OnFalseRecognition` events - it simply has no microphone wired to it - until `recognizer.AudioInputStream` is explicitly assigned a `SAPI.SpMMAudioIn` object, before `CreateRecoContext()` is called. Confirmed by adding sound/hypothesis event instrumentation during debugging: zero events without this, real dictation hypotheses and CFG recognitions with it.
  - `SpMMAudioIn.DeviceId` (real per-device selection, as opposed to whichever device Windows currently treats as default) cannot be set to anything other than its own default (-1, the classic MME `WAVE_MAPPER` convention) on this machine - assigning ANY other value throws `SPERR_ALREADY_INITIALIZED` (0x80045002), reproduced in complete isolation (a bare `Dispatch("SAPI.SpMMAudioIn"); .DeviceId = 0` in a fresh script/process, no Qt, no other app code at all, fails identically). Per-device selection from within an app is therefore unreliable via classic SAPI on this machine; the only reliable lever is changing the OS-level default recording device (Windows Sound settings).
  - `win32com` event-callback parameters (e.g. `OnRecognition`'s `Result` argument) arrive as a generic late-bound `IDispatch`, not the specific typed interface - accessing `.PhraseInfo` directly raises `AttributeError: 'PyIDispatch' object has no attribute 'PhraseInfo'`, even though the identical property works fine on an object returned directly from a `Dispatch()`'d method call. `win32com.client.CastTo(result, "ISpeechRecoResult")` resolves it - a general `win32com` event-dispatch characteristic, not SAPI-specific, and worth remembering for any future COM event-sink work in this codebase.
  - Debugging-methodology notes worth keeping for next time: a `pywin32` COM exception's real Win32/HRESULT code is buried in the exception args tuple and prints as a large negative int - `hex(value & 0xFFFFFFFF)` recovers the actual documented HRESULT (e.g. `SPERR_NOT_FOUND`, `E_INVALIDARG`) to look up. Small, disposable standalone scripts that `Dispatch()` the same COM objects directly (run via `python scratch_script.py`, never `python -c`) were far faster at isolating which single call was failing than reasoning about the app's own multi-layer wrapping - the pytest harness can't touch real COM/audio at all (by design, see "Local binaries" above's sibling rules), so this kind of live, throwaway scripting is the only way to verify COM behaviour empirically.
  - `Windows.Media.SpeechRecognition` (the WinRT API, this app's other originally-considered option alongside SAPI 5.4 - see the Product Definition Document) was NOT attempted - ruled out ahead of time in favour of Vosk given its async-only (`IAsyncOperation`) API shape needing a materially different threading model than the COM-message-pump approach above, a less mature Python projection library (`winrt`) than `pywin32`, unconfirmed microphone-permission behaviour for an unpackaged desktop Python app under Windows' privacy model, and shared underlying plumbing with the same "Voice Access" stack that already showed real gaps on this machine.
- **Ornaments/notations are parsed as label-only, findable data — never audibly realized** (survey 2026-08-21, mostly closed by Comprehensive Find P1/P3/P4 on 2026-08-28; see the "Comprehensive Find" Architecture note and `find_feature_plan.md`). What was, in the 2026-08-21 survey, "confirmed entirely unparsed" is now read by `parsers/timeline_builder.py` and surfaced as spoken Region 3/4 text and Find targets: `notations/tied` → `NoteData.tie`, `notations/slur` → `slur`, `notations/fermata` (+ shape) → `fermata`, `notations/arpeggiate`/`non-arpeggiate` on a chord note → `arpeggio` (a lone note's `<arpeggiate>` is still re-read as a Chords-part strum stroke — D7, unchanged), `time-modification` → `tuplet`, a cautionary/editorial `<accidental>` → `accidental` (D14 — a plain printed accidental is left absent, it is already spoken inside the note name), `notations/glissando`/`slide` → `glissando`, `notations/technical` marks beyond fret/string/fingering/pluck (`hammer-on`, `pull-off`, `bend`, `harmonic`, `open-string`, `up-bow`/`down-bow`, `golpe`, …) → `technique`, and a D6 catch-all (`other_notation`) for any unrecognised `<notations>` child. `direction-type/pedal`, `octave-shift`, `rehearsal`, `dashes`, `bracket` and a catch-all become structural marking targets (`DirectionSpan`/`DirectionMark`); `bar-style` double/dashed/dotted barlines (not the final `light-heavy` — D16), mid-part `<clef>` changes, and `<measure-style>` become marking points. `notations/articulations` + `notations/ornaments` already merged into `NoteData.articulation` via `models/vocabulary.py`'s `ARTICULATION_NAMES` (trill, mordent, turn, tremolo, …, with an `articulation_name()` hyphens-to-spaces fallback for anything unlisted) and that is unchanged. **The standing decision is unchanged: none of this is audibly realized** — a trill plays as the plain written note, an `<octave-shift>` does not transpose playback, a fermata does not lengthen it. Synthesizing a trill/mordent/turn needs its auxiliary pitch, which MusicXML doesn't encode directly (the diatonic neighbour under the active key, optionally altered by a sibling `<accidental-mark>` — a new inference heuristic in the spirit of `MidiTimelineBuilder._spell_pitch`); the user weighed that against grace notes' own "brief pre-note, not exact performance practice" simplification and judged the inference risk not worth it. Still genuinely unparsed: `notations/caesura`/`breath-mark` (timing, not pitch — though `breath-mark` under `<articulations>` is already caught by the wildcard merge), and `<frame>`-less rare `<direction-type>` children only via the catch-all's spoken tag.
