# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Recall Score" (repo `SReader`, remote `ScoreReader`) — a screen-reader-first music score and guitar-tab viewer/editor for visually impaired musicians. `Product Definition Document.md` is the authoritative spec: roles, numbered functional requirements with acceptance criteria, the 2x2 region layout, and the intended keystroke map. Read the relevant requirement rows before implementing a feature; most current code maps directly onto them (e.g. pickup-bar measure numbering is Ref 17, TS-relative beat/duration units is Ref 18, part/staff/voice filtering is Ref 7).

Accessibility is the product, not a polish item: notes are rendered as spoken-friendly text ("F sharp", "B double flat", octave omitted in the note list), navigation is keyboard-driven with a cyclic region focus loop, and every timeline move triggers MIDI audition. Ref 9 sets a 25 ms audition latency budget — that constraint is why the audio path is in-process FluidSynth rather than an external MIDI port. Preserve these properties when changing UI or data formatting.

## Commands

Windows, Python 3.13, dependencies in the checked-out `.venv` (not tracked):

```powershell
.venv\Scripts\python.exe main.py          # run the app
.venv\Scripts\Activate.ps1                # then plain `python main.py`
```

Dependencies are split: `requirements.txt` (runtime — PySide6 6.11, music21 10.5, pyfluidsynth 1.4), `requirements-dev.txt` (pytest, pytest-qt, pytest-cov), and `requirements-build.txt` (pyinstaller — only needed to build the Windows installer, see Packaging below). `mido` is no longer used or installed. No linter is configured.

```powershell
.venv\Scripts\python.exe -m pytest                    # whole suite (~0.6s)
.venv\Scripts\python.exe -m pytest -m "not slow"      # skip music21 tests
.venv\Scripts\python.exe -m pytest tests/models/test_music_data.py::test_name
.venv\Scripts\python.exe -m pytest --cov=models --cov=parsers --cov=widgets
```

Two invariants the harness enforces, both guarded by tests in `tests/test_harness.py`:

- **No window opens.** `tests/conftest.py` sets `QT_QPA_PLATFORM=offscreen` before PySide6 is imported.
- **No audio device opens.** An autouse fixture blocks `SynthEngine._init_engine`, so constructing a real engine in a test fails with a pointer to the fix. `MainWindow(synth=...)` accepts any object with the `SynthEngine` interface; `tests/support/null_synth.py` records calls so tests can assert what *would* have sounded.

Timeline tests must build `MusicData(file_path=...)` directly — that walks the XML with ElementTree in ~1 ms. Going through `MusicXMLReader.load()` also runs music21 at ~460 ms; those tests carry the `slow` marker.

VS Code launch config is "Python: Current File" (debugpy) — debug by opening `main.py` and pressing F5.

## Local binaries (never commit these)

`audio/synth_engine.py` needs native FluidSynth DLLs in `bin/` and a SoundFont at `soundfonts/FluidR3_GM.sf2` (~148 MB). Both directories are gitignored and exist only in the working tree.

**This is load-bearing.** The 148 MB soundfont exceeds GitHub's 100 MB file limit; committing it in August blocked all pushes and the recovery attempt cost two days of work. Never `git add` these paths, never remove those `.gitignore` entries, and if you need to restore them use `git cat-file blob <sha> > <path>` — `git checkout <commit> -- bin/` stages the files and reintroduces the problem.

If the binaries are missing the app still runs: `SynthEngine` sets `FLUIDSYNTH_AVAILABLE = False`, prints a warning, and every playback call becomes a no-op.

## Packaging (Windows installer)

Two independently runnable steps produce `dist_installer/RecallScore-Setup-<version>.exe` — a standard NSIS wizard (Welcome/Components/Directory/Start Menu/Install/Finish) that installs to Program Files (per-machine, requires admin — a deliberate choice, confirmed with the user) and registers a real uninstaller under Add/Remove Programs. Both are plain command-line tools the user runs directly (revised 2026-08-12 from an earlier version where a PowerShell wrapper did everything opaquely — the user wanted to be able to run these themselves without going through Claude):

```powershell
.venv\Scripts\python.exe -m PyInstaller packaging\RecallScore.spec --noconfirm   # from repo root
cd packaging; makensis installer.nsi   # NSIS 3.11's ${__FILEDIR__} resolves wrong given a relative path with a directory component (e.g. `makensis packaging\installer.nsi` from the repo root) - run it from inside packaging\, see installer.nsi's header comment
```

`packaging/build_installer.ps1` still exists as an **optional** one-command wrapper (`powershell -File packaging\build_installer.ps1`) that chains the two steps with a couple of sanity checks (venv present, `bin`/`soundfonts` present, finds `makensis.exe` on PATH or in one of the two standard `Program Files` locations) — neither step depends on it.

- **`version.txt`** (repo root) — the single, manually-maintained source of truth for the app version, read by `version.py` (the About dialog, `widgets/about_dialog.py`), `packaging/RecallScore.spec` (Windows exe version resource), and `packaging/installer.nsi` (installer filename/registry `DisplayVersion`). Edit it by hand to bump the version; nothing derives or auto-increments it. `version.py` resolves it via the same `sys._MEIPASS`-aware idiom as `main.py`'s `_app_icon_path()`, so it works both in dev and once `RecallScore.spec` bundles it into the frozen app.
- **`packaging/RecallScore.spec`** — PyInstaller onedir build of `main.py`, runnable standalone (see command above). Bundles `bin/*.dll` and `soundfonts/FluidR3_GM.sf2` (the gitignored local binaries above) into the frozen app so the installed app needs no separate download — this works with zero changes to `audio/synth_engine.py`'s `PROJECT_ROOT`/`BIN_DIR` resolution, because PyInstaller fakes frozen modules' `__file__` to a path under `sys._MEIPASS` matching the source tree, so `dirname(dirname(audio/synth_engine.py))` still lands on the bundle root. Excludes music21's bundled example-score corpus (`collect_data_files(..., excludes=["corpus/**", ...])`, ~58 MB) since the app only ever calls `converter.parse()` on the user's own file, never `music21.corpus` — and excludes `matplotlib`/`PIL` entirely, which music21 declares as hard dependencies purely for its unused `graph`/`audioSearch` plotting modules (confirmed via grep: only those two subpackages import matplotlib anywhere in music21). Also bundles `docs/user_guide.html` (opened from Help > User Guide, `main_window.py`'s `user_guide_html_path()`/`_show_user_guide()`, same `sys._MEIPASS`-aware resolution), `version.txt` (see above), and, if any exist, `examples/*.xml`/`*.musicxml`/`*.mxl` (opened via File > Open Example Score..., `examples_dir()`) — the last two resolved by the same `_app_base_dir()` idiom as `_app_icon_path()` below. Also regenerates `packaging/version_info.txt` from `version.txt` on every run (see below) — this used to be `build_installer.ps1`'s job, moved into the spec itself so the spec runs standalone with no wrapper script required.
- **`docs/user_guide.md`** / **`docs/user_guide.html`** — the end-user guide, reachable in-app via Help > User Guide. The `.md` is the maintained source; the `.html` is a **checked-in, manually regenerated** artifact (deliberately not a build step, to avoid making `pandoc` a build dependency) — after editing the `.md`, regenerate with `pandoc docs/user_guide.md -s --toc --metadata title="Recall Score User Guide" -o docs/user_guide.html` and commit both together.

## Architecture

Package-per-domain layout; each module holds one class. Data flows one way:

`main.py` → `MainWindow` → `MusicXMLReader.load()` → `MusicData` → four region views + `SynthEngine`

- **`models/`** — `note_data.py` (`NoteData`), `event_slice.py` (`EventSlice`), `parts_structure.py` (`PartStructureInfo`), and `music_data.py` (`MusicData`, the aggregate + timeline builder).
- **`parsers/musicXML_reader.py`** — `MusicXMLReader` builds header/metadata: credits, key, time signature, tempo, per-part structure (staff→clef, staff→voices, GM program). It parses the file **twice**: raw `ElementTree` for credits/part-list/clefs, and `music21.converter.parse` for tempo/key/time, with the ElementTree values as fallback when music21 returns nothing. `_extract_part_structure_etree`'s `<part-name>` read (→ `PartStructureInfo.name`) must match `TimelineBuilder`'s own separate `<part-name>` read (→ `NoteData.part_name`) verbatim — anything that keys off both (e.g. the Performance Report's per-instrument note tally, `MusicData.get_performance_report_lines`) silently finds nothing if they diverge. Reported bug, live-tested against `files/bach-bourree-tab/score.xml` (a real MuseScore export whose `<part-name>` is Korean, `클래식 기타` — itself just the literal translation of "Classical Guitar"): this method used to replace any part name containing a non-ASCII character with a hardcoded `"Classical Guitar"` fallback, while `TimelineBuilder` had no such filter and kept the real text — the mismatch made the report show "0 notes" for a fully-noted part. Fixed by removing the filter; there was no historical comment explaining why it existed, and every other non-ASCII-name code path in this codebase (Region 3/4's own note-attribute display, per `note.part_name` at `models/music_data.py`'s `_note_attribute_pairs`) already renders the real text unfiltered.
- **`parsers/timeline_builder.py`** — `TimelineBuilder` owns the hand-rolled `ElementTree` walk that builds `timeline_slices` (see Timeline model below). `MusicData.__post_init__` calls `TimelineBuilder(file_path, parts_info).build()`; timeline tests construct `MusicData(file_path=...)` directly, which still hits only this ElementTree pass, not music21.
- **`parsers/xml_source.py`** — `read_musicxml_root(file_path)`, the single place that turns a path into a root `Element` for both of the above. Handles compressed `.mxl` (a zip container) by reading `META-INF/container.xml`'s `rootfile` entry rather than guessing a member name — every real `.mxl` this project has seen (`files/*.mxl`) internally names that member `score.xml` regardless of the outer filename, same as this project's own uncompressed fixtures, so the manifest has to be read, not assumed.
- **`audio/synth_engine.py`** — in-process FluidSynth. At import it prepends `<root>/bin` via `os.add_dll_directory` + `PATH` and pre-loads the glib/gobject/gthread/fluidsynth DLLs with `ctypes.CDLL` before `import fluidsynth`; that ordering is required on Windows and is why the module has side effects at import time. The synth runs on the WASAPI driver at 48 kHz with a 128-frame period and 2 periods — low-latency settings chosen for Ref 9; don't raise them without cause. `fluidsynth.Synth(gain=0.7, samplerate=48000.0)` — GOTCHA, reported bug, live-tested (every note played ~a semitone sharp): `samplerate` **must** be passed to the `Synth()` constructor itself. `pyfluidsynth.Synth.__init__` calls `new_fluid_synth(self.settings)` (the actual DSP engine creation) using whatever `synth.sample-rate` is in the settings object at that exact moment, before returning; a `self._fs.setting("synth.sample-rate", ...)` call made *after* construction only updates the stored value and has no effect on the already-created engine — it silently keeps rendering at pyfluidsynth's own 44100 Hz constructor default. That mismatch (audio actually generated at 44100 Hz, WASAPI stream opened at 48000 Hz to match the real device) speeds everything up by 48000/44100, audible as ~147 cents sharp — closer to a semitone above than a whole tone, which is exactly how it was first reported. Confirmed root cause by reproducing both the broken and fixed init sequences with `fluidsynth.Synth.get_samples()` (no real audio device needed) and measuring the actual rendered frequency. WASAPI shared mode (no exclusive-mode setting anywhere in this code) is relied on to resample this fixed 48 kHz stream to whatever a given user's device actually runs at — standard OS behavior, deliberately not second-guessed with device-format detection (see tasks.txt's E10-adjacent BUG FIX entry for the user's explicit call on this). Note-off is scheduled by one single-shot `QTimer` **per sounding group**, not one shared timer — each part rings for its own `duration_ms` independent of the others (see the GM programs paragraph above). `play_chord(events, retrigger=True)`: the default silences everything currently sounding first (`stop_all_notes()`), correct for discrete audition (Ref 8 AC2 — Region 3 navigation, chord audition) where each move/press should present a clean slate. `Sequencer` passes `retrigger=False` for its natural step-to-step advance during real playback (Ref 10) — reported bug, live-tested: with the default, a new part's attack (e.g. Violin I entering mid-phrase) was silencing *other*, unrelated parts' still-ringing notes, since the old unconditional `stop_all_notes()` had no way to know the new group had nothing to do with them. `Sequencer.play_from()`/an explicit reposition still calls `stop_all_notes()` itself first, so restarting playback elsewhere does clear the deck — only the in-run advance is non-destructive.
- **`audio/metronome.py`** / **`soundfonts/recall_score_sounds.sf2`** (Ref 14, tasks.txt E11/D-14) — the click metronome's sound is a second, small, project-authored soundfont loaded by `SynthEngine._load_click_soundfont` alongside `FluidR3_GM.sf2` (its own `sfid`, `self._click_sfid`), not a synthesized tone or GM percussion — two earlier attempts at both were live-tested and rejected. Built by `tools/wav_to_sf2.py` (see `tools/README.md`) from real recorded WAV clips via a plain-text config (`tools/config.ini`, checked into git alongside its own source WAVs, e.g. `tools/click1/`/`tools/words1/`/`tools/bells/` — not gitignored, despite an earlier version of this doc claiming otherwise; `tools/example_config.ini` is the template new presets should copy from); checked into git as `soundfonts/recall_score_sounds.sf2` even though `soundfonts/` is otherwise gitignored — **GOTCHA**: a bare `soundfonts/` line makes git treat the whole directory as opaquely ignored and never evaluate a later per-file negation against it; `.gitignore` uses `soundfonts/*` (contents, not the directory itself) so the `!soundfonts/recall_score_sounds.sf2` exception actually takes effect. `click_event_for_beat()` returns `(channel, bank, program, pitch, velocity)` — accent vs. regular beat is now which *sample* plays (`program_select` onto the dedicated click soundfont), not a velocity difference on one fixed voice like the old Claves attempt. Verified against real FluidSynth, not just "the bytes parse": rendering the built soundfont and measuring the actual audio confirmed both correct sample selection per note/bank/program and, importantly, that `METRONOME_CHANNEL`'s historical GM-percussion channel (9, reserved for the old Claves approach) doesn't silently force percussion-bank lookups now that an explicit `program_select` targets a non-GM soundfont there instead (correlation 0.999 against the identical render on an ordinary channel).

  **GOTCHA, resolved 2026-08-12 (user question, tasks.txt E12's own follow-up)**: `SynthEngine.play_click`/`play_word` used to also take no `duration_ms` param but internally schedule an explicit note-off via a `QTimer`, timed from each sample's own natural length — read from a sidecar `soundfonts/recall_score_sounds.sf2.json` (`tools/wav_to_sf2.py` wrote it alongside the `.sf2`, keyed by `(bank, program, pitch)`, since different presets can validly reuse the same note numbers for unrelated sounds). That sidecar/scheduling turned out to be unnecessary and was removed: each click/word zone is a one-shot, non-looping sample (`SampleModes=0`), and FluidSynth deactivates such a voice on its own once the sample's data is exhausted, *regardless of whether a note-off was ever sent* — holding the note "on" and simply never releasing it early is sufficient to let it play to its natural end. Verified against real FluidSynth (`fluidsynth.Synth.get_samples()`, no audio device needed): rendering with no note-off at all reproduced the sample's full natural length (confirmed against the old sidecar's own recorded duration) with no hang; rendering with an early note-off reproduced the original problem this sidecar existed to avoid (abrupt cutoff via the soundfont's default near-instant release envelope). `_stop_click()`/`_stop_announcement()` (still called from `stop_all_notes()`, and from `play_click`/`play_word` themselves before a new one starts) remain the deliberate-*interrupt* path — only the "wait exactly N ms then auto-release" scheduling was removed, not the ability to cut a still-ringing one-shot short on purpose. `tools/wav_to_sf2.py` no longer writes the `.sf2.json` sidecar at all (see its own module docstring) — nothing in the app reads one anymore.

  **Panning (Ref 28, user-requested 2026-08-12)**: `_load_click_soundfont` sets a fixed MIDI pan (CC10) on each of the two reserved channels — the position announcer (`POSITION_ANNOUNCER_CHANNEL`) full left (`0`), the click (`METRONOME_CHANNEL`) full right (`127`) — once at load time, not per-call, since each channel is permanently dedicated (`MusicData.RESERVED_CHANNELS` keeps real instrument parts off both) and a channel's pan setting persists until changed. Verified against real FluidSynth: rendering at `CC10=0` produced silence on the right channel and `CC10=127` silence on the left, confirming genuine hard-left/hard-right separation.
- **`audio/position_announcer.py`** (Ref 28, tasks.txt E12) — the position announcer ("talking metronome"), built on the same custom soundfont as the click (`soundfonts/recall_score_sounds.sf2`'s `talking_metronome_default` preset, bank 0/program 0, notes 60-69 = one..seven/e/and/a per `tools/config.ini`). `spoken_word_for_beat_position(beat_position)` splits the ts-relative beat position into a whole part (1-7 → number word, Ref 28 AC3) and a fractional remainder (25/33/50/66/75% → e/and/and/a/a, AC4); `announcement_event_for_beat()` wraps that into a `(channel, bank, program, pitch, velocity)` tuple, same shape as `metronome.py`'s `click_event_for_beat()`, and both `Sequencer._sound_current_step` and `MainWindow._play_selected_region_3_notes` call it right alongside (not instead of) the existing click call, gated by its own independent `MusicData.position_announcer_enabled` (AC1/AC2) rather than the metronome's. Unlike `set_metronome_enabled`, toggling this never rebuilds `timeline_slices` — AC5 requires the announcer to only ever speak at positions that already have an event and never create its own, so there's nothing to splice in or out. **GOTCHA, real design problem**: `talking_metronome_default` and `click_default` both start their note numbering at 60, so a click and a word landing on the same beat (AC2: both can be on at once) would share a `(channel, key)` pair if sent on the same MIDI channel — FluidSynth's `noteoff(channel, key)` releases *every* voice matching that pair regardless of which preset/program started it, so an early note-off meant for one would silence both. Fixed with a second reserved channel (`POSITION_ANNOUNCER_CHANNEL = 8`, alongside the click's `METRONOME_CHANNEL = 9`) rather than asking for a disjoint note-numbering convention in the soundfont — a channel reservation holds systemically for any future click/word preset pair (the user's own stated plan), a numbering convention has to be remembered by hand every time. `MusicData.RESERVED_CHANNELS` (generalised from the old single-channel `PERCUSSION_CHANNEL` skip) keeps both channels off-limits to real instrument parts too. `SynthEngine.play_word()` is a near-duplicate of `play_click()` with its own active-note slot (`_active_announcement`) for exactly this reason, sharing `self._click_sfid` (one soundfont load already covers both presets) — see the `audio/metronome.py` bullet above for why neither method needs to schedule its own note-off at all anymore. The predicted "any future click/word preset pair" arrived with Ref 29's performance-cue sound (below), which took a third reserved channel via the identical pattern rather than reopening the disjoint-note-numbering option — confirmed with the user during design as the deliberate choice, not a default.

- **`audio/performance_cue.py`** (Ref 29) — the Performance region's (Region 5, below) "something changed, check it" audio cue: a third reserved channel, `PERFORMANCE_CUE_CHANNEL = 7` (MIDI channel 8 in 1-indexed display terms, alongside `METRONOME_CHANNEL`/`POSITION_ANNOUNCER_CHANNEL`), bank 0/program 2 (`[preset:performance_cue_default]` in `tools/config.ini`/`tools/example_config.ini`), center-panned (`_load_click_soundfont`'s third `cc(..., 10, 64)` call) since — unlike the click/announcer's deliberate hard-left/hard-right split — this cue has no directional meaning to preserve, it just needs its own channel. `performance_cue_event()` returns a fixed 5-tuple, not a beat-position lookup like `click_event_for_beat`/`announcement_event_for_beat`, since the cue fires on "the active Region 5 row set changed", not on a beat grid. `SynthEngine.play_performance_cue`/`_stop_performance_cue` are near-duplicates of `play_click`/`_stop_click` with their own `_active_performance_cue` slot, and `stop_all_notes()` calls `_stop_performance_cue()` alongside the other two so pause/stop/reposition don't leave it orphaned.
- **`tools/`** — standalone scripts, deliberately independent of the rest of the app (stdlib only, no imports from `models`/`parsers`/`audio`/etc.) so they can be run and maintained on their own. `wav_to_sf2.py` is the only one so far — see its own module docstring and `tools/README.md` for the config format.
- **`persistence/`** (Phase G, Ref 27) — Qt-aware I/O only. **The `ScoreConfig` dataclass itself lives in `models/score_config_data.py`** (R2, 2026-08-14): `MusicData` imports it, and while it sat next to `persistence/score_config.py`'s `QStandardPaths` use, importing *anything* from `models/` dragged in the whole of Qt — silently breaking the "models/ stays Qt-free" invariant that `main_window.detect_default_uk_terms()`'s placement depends on. `persistence.score_config` re-exports `ScoreConfig`, so import sites are unchanged; the JSON key codecs stayed in `persistence/` (spelling a tuple key in a file is serialisation, not data shape). `test_models_package_does_not_import_qt` (`tests/test_harness.py`) guards it, in a subprocess — the test session loads PySide6 via conftest first, so in-process `sys.modules` proves nothing. `app_settings.py` (`AppSettings`) is a single **global** file (`load()`/`save()`) for preferences independent of any score — today just `uk_terms`; `score_config.py` (`ScoreConfig`, `path_for`/`load_for`/`save`/`delete_for`) is **per-file**, keyed by the music file's own basename+extension only (`"Chessel Duet.mxl.rsc"`), never by its folder — the user can move the file and the same config is found again. **GOTCHA, live-tested (Ref 29, generalised by R1)**: `QAbstractItemView` intercepts `Key_Tab`/`Key_Backtab` at the `event()` level — its own internal cell/item-navigation handling — *before* `keyPressEvent()` is ever invoked, for a single-column view like a `QListWidget`. Ref 29 hit this on `Region5ListWidget` and fixed it there; the 2026-08-14 code review (R1, `code_review_2026-08-14.md`) found `Region2ListWidget`/`TimelineListWidget` had been carrying the same dead `keyPressEvent` handler all along. It never showed up because Qt's plain native `focusNextPrevChild()` ring (formed automatically by widget creation order, no `setTabOrder` needed) coincided with the desired cycle order for every transition except a wrap-around, and the old cycle's last region (`Region4TableWidget`, a `QTableWidget` — Tab *does* reach `keyPressEvent` there, since Tab has an intra-widget "next cell" meaning for a table) genuinely handled its own wrap. Region 5 becoming the last region put a `QListWidget` at that boundary and exposed it. A synthetic Shift+Tab (`qtbot.keyClick(widget, Qt.Key.Key_Tab, Qt.KeyboardModifier.ShiftModifier)`) also arrives as plain `Key_Tab` with `ShiftModifier` set, not as `Key_Backtab` — both conventions are checked in the mixin (`key == Qt.Key.Key_Backtab or (key == Qt.Key.Key_Tab and shift)`).

**Testing note that follows from this**: assert the cycle *method runs*, not just where focus lands — `test_every_region_routes_tab_through_the_region_cycle_not_qts_focus_chain` in `tests/test_main_window.py`. The two older cycle tests only checked the landing widget, so they passed for the entire period the handlers were dead. Likewise, drive Tab through `widget.event(...)` rather than `widget.keyPressEvent(...)` in unit tests; calling `keyPressEvent` directly (as `test_region4_table_widget.py` used to, deliberately, to route around Qt's interception) tests a path the app never takes.

GM programs are **1-indexed in the model** (25 = nylon guitar, from MusicXML `<midi-program>`) and **0-indexed on the wire** — `MusicData.get_playback_events_for_indices` does the `-1` conversion per part, so don't convert twice. Each part gets its own MIDI channel (`MusicData.get_channel_for_part`, skipping all three reserved channels in `MusicData.RESERVED_CHANNELS` — percussion channel 10/index 9, the position announcer's channel 9/index 8 (Ref 28), and the Performance region's change-cue channel 8/index 7 (Ref 29)) so a chord spanning two parts plays both instruments instead of collapsing onto `parts_info[0]`'s program (A8, Ref 8, D-5) — `SynthEngine.play_chord` / `NullSynth.play_chord` take the resulting `(channel, program, midi_notes, duration_ms)` groups and sound them together. The usable-channel list is computed fresh inside `get_channel_for_part` on each call, not cached as a class attribute — a class-body list comprehension can only see its own outermost iterable, not other class attributes referenced inside its condition (a real `NameError` hit while adding the second reservation).

`duration_ms` is per-group, not per-slice: `get_playback_events_for_indices` derives each part's own duration from the `max` `quarter_length` of *that part's* notes at this slice, not from `EventSlice.quarter_length` (which is `min()` across every note bucketed into the slice, from **every** part — see `TimelineBuilder.build`). Reported bug, live-tested against Pachelbel's Canon: a slice-wide duration meant one part's short note clamped every other part sounding at the same instant, so the cello's minims were being cut to whatever the fastest voice at that beat happened to be. `SynthEngine.play_chord` schedules note-off with one independent `QTimer` per group (not a single shared one) so this holds even across a single `play_chord` call with mixed-length groups.

### Timeline model

The timeline is a flat, sorted list of `EventSlice` — one entry per distinct `(measure, offset_in_quarters)` with at least one sounding note. Rests are skipped, so navigation lands only on attacks. `active_event_index` is the cursor; `move_timeline_left/right` return `bool` (False at the boundaries, where the spec wants an audible boundary cue that isn't implemented yet).

`TimelineBuilder.build()` (`parsers/timeline_builder.py`) is a third hand-rolled `ElementTree` pass, separate from `MusicXMLReader`. music21's stream is stored on `MusicData.score` but is **not** the source of truth for notes — the DOM walk is, because it handles `<backup>`/`<forward>` offsets, `<chord>` grouping, and `notations/technical` string/fret data explicitly.

Two conventions the parser enforces, both spec requirements:

- **Pickup bars** are detected by `implicit="yes"` or by measure 1's staff-1 content summing to less than a full bar. When present every measure number shifts down by one, so the pickup is measure **0** and the first full bar is **1**. Pickup notes get beat positions placing them at the *end* of the notional bar.
- **Beat positions and durations are relative to the time-signature denominator**, not to quarter notes. `beat_unit_quarter_len = 4.0 / denominator`; a quarter note is `ts_duration` 1.0 in 4/4 but 2.0 in 7/8. `NoteData.quarter_length` is kept separately for playback timing.
- **`notations/technical` and `notations/articulations`/`ornaments` children can repeat on one note** — e.g. a rasgueado marks one note with three `<pluck>` children (p/i/m/a) together. Always read them with `.findall()`, never `.find()` — `.find()` silently returns only the first match and drops the rest (F3's real-world bug, caught against a live MuseScore export; see `tasks.txt` F3 and the `multi_value_technical.musicxml` fixture).

**Performance markings (Ref 29)** — `TimelineBuilder._repeat_and_ending_spans`/`_hairpin_spans` are a fourth and fifth ElementTree pass (alongside the pickup/measure-start-quarters/tempo-changes passes above), each walked from a single reference part (`root.find("part")`, the same "structural, not per-voice" convention `_measure_start_quarters` uses — barlines/hairpins are score-wide, not per-voice). They populate `MusicData.repeat_spans`/`ending_spans`/`hairpin_spans` (`List[RepeatSpan]`/`List[EndingSpan]`/`List[HairpinSpan]`, `models/repeat_span.py`/`ending_span.py`/`hairpin_span.py`) as side-channel outputs, the same `tempo_changes` pattern (sparse markers scanned against the current position) — **not** a per-`EventSlice` field like `time_sig`/`key_fifths`, since spans are rare, not "in effect at literally every slice". Repeat/ending containment is a plain measure-number range check (barlines only occur at measure boundaries); hairpin containment compares `EventSlice.quarters_from_start` against `HairpinSpan.start_quarters_from_start`/`end_quarters_from_start`, since a `<wedge>` can start/stop mid-measure. `<barline>/<repeat direction="forward"|"backward">` pairs are tracked with a single "currently open forward repeat" slot (most-recent-wins on an unclosed second forward — nested repeat barlines aren't a real notation concept) and a `<barline>/<ending number type="start"|"stop"|"discontinue">` is tracked per open number, closed by the next `stop`/`discontinue` for that same number — validated against `files/bach-bourree-tab/score.xml`'s two real repeat+1st/2nd-ending passages. A backward repeat with no preceding forward defaults its start to measure 1 (the standard notation reading of an unmarked opening repeat; untested by any real file this app has seen, only by the hand-authored `tests/fixtures/unmatched_backward_repeat.musicxml`). `MusicData.total_measures` (also populated in `build()`, from `max(measure_start_quarters.keys())`) is the whole-score bar count for the Performance Report below — deliberately **not** derived from `timeline_slices`, which would undercount a trailing all-rest measure (rests are skipped from `timeline_slices` entirely).

`MusicData.get_performance_region_rows(index=None)` resolves the target slice (default the cursor) and returns two `PerformanceRegionRow`s (`models/performance_region_row.py`) per active span — a start line and an end line, repeats first then endings then hairpins, each in span-list order (a stable, deterministic order the label-diff in `MainWindow._refresh_region_5` depends on). Row wording follows one generic `"<thing> start"`/`"<thing> end"` pattern throughout (user-requested, not `"Start <thing>"`/`"End <thing>"`) — `"Repeat start: bar 2"`/`"Repeat end: bar 3"`, `"Ending 1 start"`/`"Ending 1 end"`, `"Crescendo start"`/`"Crescendo end"`. Row wording goes through `vocabulary.bar_word(uk_terms)` like the status bar, never a hardcoded "bar"/"measure" literal — "bar" vs "measure" is a dialect choice, not a fixed pick (confirmed with the user). Hairpin rows additionally append a beat position — `_bar_beat_label(bar_word, measure, beat_position)` — but only when that endpoint doesn't land on beat 1 (`"Crescendo start: bar 1 beat 3"` vs. `"Diminuendo start: bar 3"` with no beat suffix at all when it starts right on the downbeat); repeat/ending rows never need this, since barlines only occur at measure boundaries (beat 1) by construction. `slice_index_at_or_after_quarters(quarters)` and `last_visible_event_index_of_measure(measure)` (the latter mirroring the existing `first_visible_event_index_of_measure`, but scanning for the LAST match instead of the first — nothing else in the app needed a "last event in a measure" concept before) are the two lookups Region 5's Ctrl+Home/Ctrl+End use to resolve a row's jump target: a hairpin row's `jump_target_quarters` is set (a wedge can start/stop mid-measure) so it always uses the quarters-based lookup; a repeat/ending row's is `None`, resolved via the plain measure lookup instead — Ctrl+Home uses `first_visible_event_index_of_measure`, Ctrl+End uses `last_visible_event_index_of_measure` (the user's own decision: "the end of it" means the *last* sounding note of the end bar, not the first). `MusicData.get_performance_report_lines()` (Edit > Performance Report..., `widgets/performance_report_dialog.py`) is a separate, read-only, whole-score summary — reuses `get_region_1_data()` wholesale (not cherry-picked keys, since `credits_dict`'s keys come from each file's own `<credit-type>` text and aren't guaranteed to match a fixed name like "Title"), counts notes per instrument from `_real_timeline_slices` (the whole score, ignoring the current Region 2 filter — the report describes the piece, not the current filtered view), and lists `repeat_spans`/`ending_spans`/`hairpin_spans` by bar range. No jump-to-location navigation from the report — an explicit scope cut from the user for this iteration, unlike Region 5's own Ctrl+Home/Ctrl+End.

`MainWindow._refresh_region_5` is hooked into the single choke point `_update_timeline_views` (unconditional of `play_all`) rather than scattered across every navigation method — confirmed exhaustive by reading `main_window.py`/`audio/sequencer.py` in full: every path that moves `active_event_index` (arrow/measure/typed-measure navigation, Home/End, Region 2 filter changes, Sequencer/Ref-10 playback stepping, initial load) already funnels through there. It diffs the new row-label list against `self._last_performance_row_labels` and skips the rebuild (not just the audio cue) when unchanged, so Region 5's own focus/selection isn't reset on every navigation step while the cursor stays inside the same span(s). **GOTCHA, live-tested**: that sentinel must start as `None`, not `[]` — starting it at `[]` made the very first render (an empty opening position, whose own rows are also `[]`) compare equal and get silently skipped, leaving Region 5 with no items at all rather than its documented "None" placeholder row.

**GOTCHA, reported bug, live-tested**: `_update_timeline_views` calls `_play_selected_region_3_notes()` (when `play_all`) **before** `_refresh_region_5()`, not after — the cue was audible during Space-driven playback but silent on every manual navigation step (arrow keys, Ctrl+arrow, Home/End, typed-measure jump) until this was fixed. `_play_selected_region_3_notes` calls `synth.play_chord(events)` with its default `retrigger=True`, which calls `stop_all_notes()` first thing (A8) — with the cue fired first, that `stop_all_notes()` landed a fraction of a second later and cut the just-started cue off almost immediately. Playback never hit this because `_on_sequencer_step` calls `_update_timeline_views(play_all=False)`, so `_play_selected_region_3_notes()` never runs there at all — the Sequencer already sounded its own chord via `_sound_current_step`'s `retrigger=False`, which never calls `stop_all_notes()` (see the GM programs paragraph above). Fixed by reordering: sound the notes (and their retrigger-driven silence-everything) first, then fire the cue on its own untouched reserved channel afterward.

### Selection-driven regions

Region 3 is `ExtendedSelection` and defaults to selecting every note in the current slice (`Ctrl+A` reselects all). Regions 4 and audio follow the **selection**, not the slice: `get_region_4_data_for_indices(indices)` and `get_midi_notes_for_indices(indices)` take Region 3's selected rows. `_update_timeline_views(play_all=...)` blocks Region 3's signals during a rebuild to avoid audition storms, then fires playback once. `get_region_3_data()` and all three indices-taking accessors read through `MusicData._visible_notes()` first, which filters the current slice's notes by `active_voice_filter` — the `(part_id, staff, voice)` set Region 2 maintains (Ref 7) — so a selected row index always means the same note in Region 3, Region 4 and playback even when some notes are hidden. Keep view code reading through these accessors rather than reaching into `timeline_slices`.

After any Region 3 rebuild that calls `selectAll()`, also call `region_3.setCurrentRow(0, QItemSelectionModel.SelectionFlag.NoUpdate)` **outside** the `blockSignals` window (`_update_timeline_views` does this). `selectAll()` marks rows selected but deliberately leaves the view's own "current" item untouched, and Qt's accessibility bridge needs a definite current item to tell NVDA which note to announce — with several notes selected NVDA still gets a selection-changed announcement, but with exactly one note there was nothing pointing at it (live-tested bug, F3). The explicit `NoUpdate` flag is required — the plain one-arg `setCurrentRow(0)` was believed to default to `NoUpdate` and leave `selectAll()`'s selection alone, but in this PySide6 version it doesn't: it collapses the selection down to just row 0, silently turning "moving onto a chord sounds every note in it" into "only the first note sounds" (live-tested regression, caught after F2). Always pass the flag explicitly; don't rely on the one-arg overload's default here.

Region 3's row text and Region 4's rows both go through an attribute system beyond the bare note name (Ref 15 AC4), split into a WHICH half (F1) and an ORDER half (F2). WHICH: `voice_display_attributes` (keyed by `(part_id, staff, voice)`) is which optional keys (`string`, `fret`, `dynamic`, `articulation`, `fingering`, `pluck`, ...) are switched on per voice — defaulting to just `{"step"}`. `_note_attribute_pairs(note)` returns only the keys that note actually has a value for, so a key renders in Region 3/4 only when it's **both** toggled on for that voice **and** present on the note; absence isn't a bug; it's the mechanism. `set_display_attribute(key, scope, notes, add)` fans a toggle out across `"voice"/"stave"/"part"/"score"` scope, driven by Region 4's context menu (`Region4TableWidget`). ORDER: `MusicData.attribute_order` is the live, mutable, per-instance rendering order both `_format_note_for_region_3` and `_region_4_rows` iterate — `DISPLAY_ATTRIBUTE_ORDER` is only the fixed *default* every fresh `MusicData` starts from (`__post_init__`), not what actually renders. `move_attribute_order(key, up, within=...)` reorders it; `attribute_keys_for_voices(voice_tuples)` scans the whole score (not just the current slice) for which keys are relevant to a scope. `attribute_order`, unlike `uk_terms`, is **per-score** (Phase G, Ref 27) — persisted via `persistence/score_config.py` and restored in `_on_score_loaded` through `MusicData.apply_config`; a fresh `MusicData` with no saved config falls back to `DISPLAY_ATTRIBUTE_ORDER`. Options > Reorder Attributes... (`widgets/attribute_order_dialog.py`, `AttributeOrderDialog`) is the F2 UI: scoped to whichever part/staff/voice is selected in Region 2 (`Region2ListWidget.current_node()`, `region2_manager.voice_tuples_for_node()`), Move Up/Move Down buttons (Alt+U/Alt+D mnemonics) move the selected attribute live. It deliberately doesn't duplicate F1's add/remove menu. Adding a new optional per-note attribute (as F3 did for dynamic/articulation/fingering/pluck) needs no UI work at all — append it to `DISPLAY_ATTRIBUTE_ORDER` and `_note_attribute_pairs`, and the toggle menu, scope fan-out, ordering, and omit-if-absent rendering all pick it up automatically.
